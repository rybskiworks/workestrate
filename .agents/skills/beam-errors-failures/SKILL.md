# BEAM Errors and Failures

## Triggers

Load this skill when:

- Writing or reviewing error-handling code in BEAM languages.
- Using `try/catch` and deciding between exception classes.
- Choosing error tuples vs exceptions vs letting a process crash.
- Using links or monitors for failure detection and propagation.
- Debugging a crash, exit-signal cascade, or supervisor restart loop.

## Key Rules

- Three exception classes: `error` (raised by `erlang:error/1` or runtime
  faults), `exit` (raised by `exit/1`), and `throw` (raised by `throw/1`); all
  three can be generated by `erlang:raise/3`.
- `try ... catch Class:Reason:Stacktrace -> ... end` distinguishes classes;
  plain `catch Expr` cannot.
- Common exit reasons: `normal`, `kill`, `shutdown`, `{shutdown, term()}`, and
  error reasons `badarg`, `badarith`, `{badmatch, V}`, `function_clause`,
  `{case_clause, V}`, `undef`, `noproc`, `noconnection`, `system_limit`.
- `exit/1` raises an exception of class `exit` in the CALLING process; if
  uncaught it terminates the caller and emits exit signals with the same reason
  to all linked processes/ports.
- `exit_signal/2,3` (OTP 27+ documentation; introduced OTP 24+; formerly
  `exit/2`) sends an exit signal to another process/port WITHOUT establishing a
  link. The signal's `link` flag is NOT set. Use it instead of `exit/2` for new
  code.
- `kill` distinction:
  - `exit_signal(Pid, kill)` is untrappable; the receiver terminates with reason
    `killed`.
  - A `kill` signal received via a LINK (`link` flag set) CAN be trapped; it is
    converted to `{'EXIT', SenderID, kill}` and is NOT converted to `killed`.
- Exit-signal reception rules (from `ref_man_processes.html`):
  1. Silently dropped if: the `link` flag is set and the corresponding link is
     deactivated; OR the reason is `normal` and the receiver is NOT trapping
     exits.
  2. Receiver terminated if: the `link` flag is NOT set and the reason is `kill`
     (terminates with `killed`); OR the receiver is NOT trapping exits and the
     reason is other than `normal` (if the `link` flag is set, the link must be
     active). The exit reason equals the signal's reason; a link-originated
     `kill` is NOT converted to `killed`.
  3. Converted to message `{'EXIT', SenderID, Reason}` if: the receiver IS
     trapping exits, and either the `link` flag is NOT set and the reason is not
     `kill`, OR the `link` flag is set and the link is active. A `kill` reason in
     this case does NOT terminate the receiver and is NOT converted to `killed`.
- `process_flag(trap_exit, true)` converts exit signals into
  `{'EXIT', From, Reason}` messages. `normal` exit signals are silently dropped
  unless the receiver is trapping exits.
- Monitor message `{'DOWN', Ref, process, Pid, Reason}` is unidirectional;
  `noproc` is delivered immediately if the process did not exist when monitoring
  began. Use `demonitor(Ref, [flush])` to remove a monitor and discard a queued
  `DOWN`.
- Let it crash: processes should crash on unexpected input instead of defensive
  programming; supervisors restart them. Fault tolerance comes from isolation
  plus restart, not from catching every possible error.
- Crash vs return value: a crash is abnormal termination that propagates exit
  signals; a return value, even `{error, ...}`, is normal control flow and does
  not propagate.
- Stacktrace: list of `{Module, Function, Arity, ExtraInfo}` (and/or
  `{Fun, Arity, ExtraInfo}`); rely on it only for debugging. Tail-call
  optimization, depth limits, and compiler changes can truncate or alter it.
  The only guarantee is that `error:undef` includes the attempted
  `Module`, `Function`, and `Arity` as the first entry.
- `erlang:raise/3`: `raise(Class, Reason, Stacktrace)` where `Class` is one of
  `error`, `exit`, or `throw`.
- Atom exhaustion: atoms are never garbage-collected and the emulator terminates
  when the default atom limit (1,048,576) is reached. Never call
  `list_to_atom/1` or `binary_to_atom/1,2` on untrusted or dynamic input; use
  `list_to_existing_atom/1` or `binary_to_existing_atom/1,2`.
- NIFs should be a last resort; too much work degrades VM responsiveness, too
  little work wastes NIF call overhead.

## Quick Commands

```erl
try Expr catch
  error:Reason:St -> ...;
  exit:Reason:St  -> ...;
  throw:Value     -> ...
end.
exit(normal).                         %% stop calling process
exit_signal(Pid, shutdown).            %% signal another process (OTP 24+)
process_flag(trap_exit, true).
monitor(process, Pid).
demonitor(Ref, [flush]).
erlang:system_info(atom_count).
process_info(Pid, trap_exit).
```

## Anti-patterns

- Catching exceptions to silence them without fixing the underlying cause.
- Using `trap_exit` casually outside supervisors or resource-owning processes.
- Confusing `{error, Reason}` return values with crashes and exit signals.
- Relying on stacktraces for control flow instead of debugging only.
- Using `exit_signal/2` when `exit/1` was intended, or vice versa.
- Defensive programming where letting the process crash and restarting via a
  supervisor is the correct design.
- Calling `list_to_atom/1` or `binary_to_atom/1,2` on untrusted input.
