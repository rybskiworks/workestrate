## Purpose
This page is a guide explaining what a Software Bill of Materials (SBoM) is, why
to generate one, and how to produce one for a Gleam project using the OSS Review
Toolkit (ORT). It does NOT document a native `gleam export` SBOM command — Gleam
itself has no built-in SBOM generator. Instead, SBoM generation is delegated to
ORT, which consumes the Gleam project (notably `manifest.toml`) as input.

## SBOM/dependency manifest generation (commands + output format)
There is no `gleam export` subcommand for SBOM. Generation is performed by ORT
in three stages, each run as a Docker container against the project root.

### 1. Dependency analysis (analyzer)
```sh
docker run --rm \
  -v "$(pwd)":/workspace \
  -w /workspace \
  ghcr.io/oss-review-toolkit/ort-minimal:74.0.0 \
  analyze \
    --input-dir /workspace \
    --output-dir /workspace/ort-result
```
Produces: `ort-result/analyzer-result.yml`
Requirement: `manifest.toml` must be checked into version control and reflect
the current project state.

### 2. Scanning (scanner)
```sh
docker run --rm \
  -v "$(pwd)":/workspace \
  -w /workspace \
  ghcr.io/oss-review-toolkit/ort-minimal:74.0.0 \
  scan \
    --input-file /workspace/ort-result/analyzer-result.yml \
    --output-dir /workspace/ort-result
```
Produces: `ort-result/scan-result.yml` (collects licence + copyright metadata).

### 3. Report generation (reporter)
```sh
docker run --rm \
  -v "$(pwd)":/workspace \
  -w /workspace \
  ghcr.io/oss-review-toolkit/ort-minimal:74.0.0 \
  report \
    --input-file /workspace/ort-result/scan-result.yml \
    --output-dir /workspace/ort-result \
    --report-formats CycloneDx,SpdxDocument,WebApp \
    --option CycloneDX=output.file.formats=json,xml \
    --option SpdxDocument=outputFileFormats=JSON,YAML
```
Produces SBoMs in ORT's default report locations under `ort-result/` in:
- CycloneDX (JSON + XML)
- SPDX (JSON + YAML)
- WebApp (HTML viewer)

## Lockfile/manifest
The page references `manifest.toml` as the canonical dependency lockfile that
ORT consumes. It must be committed to version control and reflect the current
project state for accurate analysis. (This is Gleam's transitive-dependency
lockfile generated by `gleam deps`/`gleam fetch`.) No other lockfile is named.

## Package provenance & metadata
An SBoM (per the page's definition) typically includes:
- Direct and transitive dependencies
- Package names and versions
- Source locations
- Cryptographic hashes
- Licence and copyright information

ORT's scan stage is what collects the licence + copyright metadata; the
analyzer stage resolves direct + transitive dependencies. The page does not
detail per-package provenance fields beyond the standard SBoM contents above.

## Hex integration
Not explicitly described. ORT resolves Gleam dependencies (Hex packages) via the
`manifest.toml` / project manifest rather than via a direct Hex API call. The
page does not name Hex or `hex.pm` directly; integration is implicit through
Gleam's own dependency resolution feeding `manifest.toml`.

## Strict rules
- `manifest.toml` MUST be checked into version control and reflect current state
  for accurate analyzer results.
- SBoMs should be generated automatically and kept up to date (CI integration
  recommended).
- An SBoM does NOT claim software is secure, compliant, or vulnerability-free;
  it is only a factual foundation for other tools.
- Use the `ort-minimal` image (sufficient for Gleam projects).
- All commands assume execution from the project root.
