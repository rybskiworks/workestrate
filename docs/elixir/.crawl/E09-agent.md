## Purpose
Agents are a simple abstraction around state. The `Agent` module provides a
basic server implementation that allows state to be retrieved and updated via a
simple API. Often in Elixir there is a need to share or store state that must be
accessed from different processes or by the same process at different points in
time. Thanks to the agent server process, state can be safely mutated
concurrently.

## Key functions
- `start_link(fun, options \\ [])` — starts an agent linked to the current
  process with the given function. Returns `{:ok, pid} | {:error, ...}`.
- `start_link(module, fun, args, options \\ [])` — MFA variant (for distributed
  / hot-code-swap safety).
- `start(fun, options \\ [])` — starts an agent without links (outside a
  supervision tree).
- `start(module, fun, args, options \\ [])` — MFA variant of `start/2`.
- `get(agent, fun, timeout \\ 5000)` — gets a value via an anonymous function
  invoked inside the agent (server). Default timeout 5000ms; on timeout the call
  fails and the caller exits.
- `get(agent, module, fun, args, timeout \\ 5000)` — MFA variant.
- `get_and_update(agent, fun, timeout \\ 5000)` — gets and updates the state
  atomically in one operation; `fun` returns `{reply, new_state}`.
- `get_and_update(agent, module, fun, args, timeout \\ 5000)` — MFA variant.
- `update(agent, fun, timeout \\ 5000)` — updates state; return value of `fun`
  becomes the new state. Always returns `:ok`.
- `update(agent, module, fun, args, timeout \\ 5000)` — MFA variant.
- `cast(agent, fun)` — fire-and-forget cast; returns `:ok` immediately
  regardless of whether the agent (or its node) exists.
- `cast(agent, module, fun, args)` — MFA variant of cast.
- `stop(agent, reason \\ :normal, timeout \\ :infinity)` — synchronously stops
  the agent with the given reason. Returns `:ok` if it terminates with the
  reason; otherwise the call exits. Keeps OTP error-reporting semantics: a
  reason other than `:normal`, `:shutdown`, or `{:shutdown, _}` logs an error
  report.
- `child_spec(arg)` — returns a supervision child spec (generated by
  `use Agent`).

Types: `agent() :: pid() | {atom(), node()} | name()`;
`name() :: atom() | {:global, term()} | {:via, module(), term()}`;
`on_start() :: {:ok, pid()} | {:error, {:already_started, pid()} | term()}`;
`state() :: term()`.

## Agent vs GenServer guidance
- Agent is a thin wrapper around a GenServer: it exposes a minimal
  client/server API for holding and mutating a single piece of state via
  anonymous functions (or MFA tuples). It is the right tool when you only need
  to share/store simple state with no custom message handling.
- Agents provide a segregation between the client and server APIs (similar to
  GenServers). The functions passed to `Agent.get/update/get_and_update` are
  invoked inside the agent (the server). Avoid expensive operations inside the
  agent, as they block the agent until the request is fulfilled.
- Prefer computing in the client (`Agent.get(agent, & &1) |> expensive()`)
  when state is small and atomicity is not required; compute in the server
  (`Agent.get(agent, fn s -> expensive(s) end)`) when state is large or when the
  operation must be atomic to avoid race conditions between concurrent updaters.
- Reach for a full `GenServer` (or `use GenServer`) when you need custom
  `handle_call/handle_cast/handle_info` callbacks, timed messages, non-trivial
  initialization, or anything beyond get/update of a single state value.
- `use Agent` defines a `child_spec/1` so the module can be used as a
  supervision child; options `:id`, `:restart` (default `:permanent`),
  `:shutdown` customize it. Name registration follows the same rules as
  GenServers.

## Agent ↔ BEAM gen_server mapping (→ docs/beam/gen-server.md)
An Elixir `Agent` is implemented on top of the BEAM `gen_server` behaviour.
Conceptual mapping:

| Agent API | Underlying gen_server mechanism |
| --- | --- |
| `start_link(fun, opts)` | `gen_server:start_link/3,4` with init returning `{ok, fun.()}` |
| `start(fun, opts)` | `gen_server:start/3,4` (unlinked) |
| `get(agent, fun, timeout)` | `gen_server:call/3` → `handle_call` runs `fun(State)` and replies |
| `get_and_update(agent, fun, timeout)` | `gen_server:call/3` → `handle_call` runs `fun`, replies with `reply`, sets `new_state` |
| `update(agent, fun, timeout)` | `gen_server:call/3` → `handle_call` runs `fun`, replies `:ok`, sets new state |
| `cast(agent, fun)` | `gen_server:cast/2` → `handle_cast` runs `fun`, sets new state |
| `stop(agent, reason, timeout)` | `gen_server:stop/3` (or `gen_server:call` to terminate) |
| MFA variants (`module, fun, args`) | same callbacks but the function is referenced by MFA rather than sent as a closure — required for distributed agents / rolling upgrades where the caller and server may run different module versions |
| `use Agent` `child_spec/1` | standard supervisor child spec (`:id`, `:restart`, `:shutdown`) |

Notes for docs/beam/gen-server.md cross-reference:
- Agent collapses the `handle_call`/`handle_cast` contract into "run this
  function against the state". There is no `handle_info`, no `handle_continue`,
  no custom init beyond the initial-state function, and no code_change callback
  exposed to the user (hot code swapping is done via the MFA `appup` instruction
  `{Enum, :into, [%{}]}` style shown in the page).
- Default call timeout is 5000ms (vs `gen_server`'s 5000ms default); on timeout
  the caller exits, matching `gen_server:call` timeout semantics.
- `cast/2` returns `:ok` immediately and is lossy if the agent/node is gone,
  matching `gen_server:cast/2`.

## Strict rules
- The function passed to `get/get_and_update/update/cast` runs **inside the
  agent process** (the server), not the caller. Keep it cheap; long work blocks
  all other clients of that agent.
- `update` and `cast` mutate state; `update` is synchronous (returns `:ok`
  after the state is updated), `cast` is fire-and-forget.
- `get_and_update` is the only atomic read-modify-write. Doing
  `get` then `update` separately is **not atomic** and races concurrent
  updaters.
- Default timeout for `get/get_and_update/update` is 5000ms; on timeout the
  caller **exits**. Use `:infinity` only when truly needed.
- `stop` keeps OTP error-reporting semantics: reasons other than `:normal`,
  `:shutdown`, or `{:shutdown, _}` log an error report.
- In distributed setups or rolling upgrades, use the **MFA** variants
  (`module, fun, args`), not anonymous functions, because anonymous-function
  closures only work when caller and agent share the same version of the
  caller module.
- `use Agent` generates `child_spec/1`; do not hand-roll a child spec unless
  customizing `:id`/`:restart`/`:shutdown` via `use Agent, ...`.

## Version notes
- Page title: "Agent — Elixir v1.20.2".
- `use Agent` generates `child_spec/1` with `:restart` default `:permanent`
  and configurable `:id`/`:shutdown`.
- Hot code swapping is supported via the MFA `appup` update instruction, e.g.
  `{:update, :sample, {:advanced, {Enum, :into, [%{}]}}}`; the agent's state is
  prepended to the argument list.
- No `handle_info`/`handle_continue`/`code_change` callbacks are exposed to the
  Agent user — these are gen_server concepts absorbed inside the Agent
  implementation.
