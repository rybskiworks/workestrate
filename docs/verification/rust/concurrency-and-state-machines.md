# Concurrency and State Machines

Verified concurrency is Verus's most advanced and differentiated capability. It is built on the **VerusSync framework**, a token-based separation-logic discipline for programs that require a *nontrivial ownership discipline* — multi-threaded concurrent code, and frequently also code that needs `unsafe` features (raw pointers, `UnsafeCell`).

> **Note:** This is advanced material. The Verus state-machines guide itself is marked "a work-in-progress." Where the upstream docs are incomplete or marked TODO, this page says so explicitly. Treat any statement flagged *(uncertain)* as needing confirmation against a running Verus before relying on it.

This page covers: atomic operations and ghost state, invariants, the verified `RwLock`, the `state_machine!` / `tokenized_state_machine!` macros, the VerusSync tokenization strategies (PCM resource algebra), prophecy variables, and the canonical teaching examples. For the basics of `spec`/`proof`/`exec` modes, see [verification-model.md](./verification-model.md); for proof tactics used inside concurrent proofs, see [proofs.md](./proofs.md).

## What VerusSync is for

From the state-machines guide intro, the unifying theme is programs that require some kind of **nontrivial ownership discipline**, where different objects that might be "owned independently" need to coordinate somehow:

- Locks need to manage ownership of some underlying resource between multiple clients.
- Reference-counted smart pointers need to coordinate to agree on a reference-count.
- Concurrent data structures (queues, hash tables, and so on) require their client threads to coordinate their access to the data structure.

This kind of nontrivial ownership is implemented through Verus's `tokenized_state_machine!` utility. The guide also notes these techniques are "actually useful for single-threaded code, too" and for "verifying **code that needs unsafe features** (especially raw pointers and unsafe cells)."

The guide expects "general familiarity with Verus," including proficiency with `spec`, `proof`, and `exec` modes, and `ghost` and `exec` variables.

## Atomic operations

Verus provides two layers of verified atomics in `vstd`:

1. **Permissioned atomics** (`vstd/atomic.rs`): `PAtomicU64`, `PAtomicU32`, etc., each paired with a tracked `Permission` token (`PermissionU64`, …). Every load/store/compare-exchange requires presenting the matching permission.
2. **Ghost-carrying atomics** (`vstd/atomic_ghost.rs`): `AtomicU64<K, G, Pred>`, etc., which wrap a permissioned atomic *and* an `AtomicInvariant` holding both the permission and an arbitrary ghost value `G`, related by a user-supplied `AtomicInvariantPredicate`.

### Permissioned atomics

The permissioned atomic types are generated by macros. Each `PAtomic*` is `#[verifier::external_body]` (trusted), and each operation is annotated `#[verifier::atomic]` with `opens_invariants none` — meaning the operation is atomic for the purposes of `open_atomic_invariant!`, but it does *not* itself open any invariant. Verbatim from `vstd/atomic.rs`, the `load` and `store` signatures:

```rust
#[inline(always)]
#[verifier::external_body] /* vattr */
#[verifier::atomic] /* vattr */
pub fn load(&self, Tracked(perm): Tracked<&$p_ident>) -> (ret: $value_ty)
    requires
        equal(self.id(), perm.view().patomic),
    ensures equal(perm.view().value, ret),
    opens_invariants none
    no_unwind
{
    return self.ato.load(Ordering::SeqCst);
}

#[inline(always)]
#[verifier::external_body] /* vattr */
#[verifier::atomic] /* vattr */
pub fn store(&self, Tracked(perm): Tracked<&mut $p_ident>, v: $value_ty)
    requires
        equal(self.id(), old(perm).view().patomic),
    ensures equal(final(perm).view().value, v) && equal(self.id(), final(perm).view().patomic),
    opens_invariants none
    no_unwind
{
    self.ato.store(v, Ordering::SeqCst);
}
```

The concrete types are instantiated as (verbatim from `vstd/atomic.rs`):

```rust
make_bool_atomic!(PAtomicBool, PermissionBool, PermissionDataBool, AtomicBool, bool);
make_unsigned_integer_atomic!(PAtomicU8, PermissionU8, PermissionDataU8, AtomicU8, u8, u8_specs);
make_unsigned_integer_atomic!(
    PAtomicU32, PermissionU32, PermissionDataU32, AtomicU32, u32, u32_specs);
make_unsigned_integer_atomic!(
    PAtomicU64, PermissionU64, PermissionDataU64, AtomicU64, u64, u64_specs);
```

Each `PAtomic*` comes with a tracked `Permission*` struct whose `view()` exposes `patomic: int` (the cell id) and `value`. The `is_for`, `points_to`, `value`, and `id` spec functions (verbatim):

```rust
pub open spec fn is_for(&self, patomic: $at_ident) -> bool {
    self.view().patomic == patomic.id()
}

pub open spec fn points_to(&self, v: $value_ty) -> bool {
    self.view().value == v
}

#[verifier::inline]
pub open spec fn value(&self) -> $value_ty {
    self.view().value
}

#[verifier::inline]
pub open spec fn id(&self) -> AtomicCellId {
    self.view().patomic
}
```

### Ghost-carrying atomics: `atomic_with_ghost!`

The `atomic_ghost` layer associates a ghost value `G` with each atomic cell, guarded by an `AtomicInvariantPredicate`:

```rust
pub trait AtomicInvariantPredicate<K, V, G> {
    spec fn atomic_inv(k: K, v: V, g: G) -> bool;
}
```

The `AtomicU64<K, G, Pred>` struct holds a `patomic: PAtomicU64` and an `atomic_inv: Tracked<AtomicInvariant<(K, int), (PermissionU64, G), AtomicPredU64<Pred>>>`. Its `new` (verbatim from `vstd/atomic_ghost.rs`):

```rust
#[inline(always)]
pub const fn new(Ghost(k): Ghost<K>, u: $value_ty, Tracked(g): Tracked<G>) -> (t: Self)
    requires Pred::atomic_inv(k, u, g),
    ensures t.well_formed() && t.constant() == k,
{
    let (patomic, Tracked(perm)) = $patomic_ty::new(u);
    let tracked pair = (perm, g);
    assert(Pred::atomic_inv(k, u, g));
    assert(perm.view().patomic == patomic.id());
    let tracked atomic_inv = AtomicInvariant::new(
        (k, patomic.id()), pair, 0);
    $at_ident { patomic, atomic_inv: Tracked(atomic_inv), }
}
```

The workhorse is the `atomic_with_ghost!` macro. Its general syntax (verbatim from the `vstd/atomic_ghost.rs` doc comment):

```rust
let result = atomic_with_ghost!(
    $atomic => $operation_name($operands...);
    update $prev -> $next;         // `update` line is optional
    returning $ret;                // `returning` line is optional
    ghost $g => {
        /* Proof code with access to `tracked` variable `g: G` */
    }
);
```

At the start of the ghost block, the user may assume the operation's specification relation on `(prev, next, ret)` *and* that `atomic.inv(prev, g)` holds; the user must update `g` so that `atomic.inv(next, g)` holds at the end. The supported operations and their specifications (verbatim table):

| operation | specification |
|---|---|
| `load()` | `next == prev && ret == prev` |
| `store(x)` | `next == x && ret == ()` |
| `swap(x)` | `next == x && ret == prev` |
| `compare_exchange(x, y)` | `prev == x && next == y && ret == Ok(prev)` ("success") OR `prev != x && next == prev && ret == Err(prev)` ("failure") |
| `fetch_add(x)` (*) | `next == prev + x && ret == prev` |
| `fetch_sub(x)` (*) | `next == prev - x && ret == prev` |
| `fetch_or(x)` | `next == prev \| x && ret == prev` |
| `fetch_and(x)` | `next == prev & x && ret == prev` |
| `fetch_max(x)` | `next == max(prev, x) && ret == prev` |
| `no_op()` (**) | `next == prev && ret == ()` |

(*) `fetch_add`/`fetch_sub` do *not* specify wrapping-on-overflow; the user must prove overflow does not occur. `fetch_add_wrapping`/`fetch_sub_wrapping` are the wrapping variants. (**) `no_op` is entirely ghost — it emits no instruction, letting you access ghost state and the stored value as `spec` data without a load.

## Invariants: `AtomicInvariant` and `LocalInvariant`

Both are ghost objects providing "interior mutability" for `tracked` ghost objects, specified by an `InvariantPredicate`:

```rust
pub trait InvariantPredicate<K, V> {
    spec fn inv(k: K, v: V) -> bool;
}
```

- **`AtomicInvariant<K, V, Pred>`** implements `Sync` and may be shared between threads — but can only be opened for the duration of a single *sequentially consistent atomic* operation (via `open_atomic_invariant!`).
- **`LocalInvariant<K, V, Pred>`** is never `Sync` (cannot be shared between threads) but can be opened for an indefinite length of time (via `open_local_invariant!`).

The `vstd/invariant.rs` source summarizes the `Sync`/`Send` implications (verbatim):

```
//    T                   AtomicInvariant<T>  LocalInvariant<T>
//
//    {}          ==>     {}                  {}
//    Send        ==>     Send+Sync           Send
//    Sync        ==>     {}                  {}
//    Sync+Send   ==>     Send+Sync           Send
```

The docs recommend using the `atomic_ghost` APIs directly rather than `AtomicInvariant` by hand.

## The verified `RwLock`

`vstd/rwlock.rs` is a fully verified reader-writer lock built on atomics, a `PCell`, and a `tokenized_state_machine_vstd!`. It is parameterized by a predicate `Pred: RwLockPredicate<V>`:

```rust
pub trait RwLockPredicate<V>: Sized {
    spec fn inv(self, v: V) -> bool;
}
```

The lock itself (verbatim):

```rust
pub struct RwLock<V, Pred: RwLockPredicate<V>> {
    cell: un::PCell<V>,
    exc: AtomicBool<_, RwLockToks::flag_exc<(Pred, CellId), un::PointsTo<V>, InternalPred<V, Pred>>, _>,
    rc: AtomicUsize<_, RwLockToks::flag_rc<(Pred, CellId), un::PointsTo<V>, InternalPred<V, Pred>>, _>,
    inst: Tracked<RwLockToks::Instance<(Pred, CellId), un::PointsTo<V>, InternalPred<V, Pred>>>,
    pred: Ghost<Pred>,
}
```

The public API: `new`, `acquire_write` (returns `(V, WriteHandle)`), `acquire_read` (returns `ReadHandle`), `WriteHandle::release_write`, `ReadHandle::borrow`, `ReadHandle::release_read`. Two important caveats from the docs: the lock is **not** released automatically on drop (you must call `release_*`), and the specification does *not* verify absence of deadlocks.

The `acquire_write` implementation uses `atomic_with_ghost!` with `compare_exchange` on the `exc` flag, then a busy-wait `load` on `rc` until it reaches 0 — exchanging ghost tokens through the state machine at each atomic step (verbatim snippet):

```rust
let result =
    atomic_with_ghost!(
    &self.exc => compare_exchange(false, true);
    returning res;
    ghost g =>
{
    if res is Ok {
        token = Option::Some(self.inst.borrow().acquire_exc_start(&mut g));
    }
});
```

The underlying `RwLockToks` state machine uses `constant`, `variable`, `storage_option`, `option`, and `multiset` sharding strategies (see below).

## The `state_machine!` macro

The `state_machines_macros` library provides two macros: `state_machine!` (basic, non-tokenized) and `tokenized_state_machine!` (the full VerusSync system). A basic state machine has four components: the state definition, the transitions (including initialization), invariants, and proofs that the invariants hold. The canonical minimal example (verbatim from `components.md`):

```rust
state_machine!{
    AdderMachine {
        //// The state definition
        
        fields {
            pub number: int,
        }
        
        //// The transitions

        init!{
            initialize() {
                init number = 0;
            }
        }   

        transition!{
            add(n: int) {
                update number = pre.number + 2*n;
            }
        }
        
        //// Invariants on the state

        #[invariant]
        pub fn is_even(&self) -> bool {
            self.number % 2 == 0
        }
        
        //// Proofs that the invariants hold

        #[inductive(initialize)]
        fn initialize_inductive(post: Self) {
            // Verus proves that 0 % 2 == 0
        }

        #[inductive(add)]
        fn add_inductive(pre: Self, post: Self, n: int) {
            // Verus proves that if `pre.number % 2 == 0` then
            // `post.number` is `pre.number + 2*n` is divisible by 2 as well.
        }
    }
}
```

### The four operation kinds

| | `init!` | `transition!` | `readonly!` | `property!` |
|---|---|---|---|---|
| `init` | yes | | | |
| `update` | | yes | | |
| `require` | yes | yes | yes | yes |
| `assert` | | yes | yes | yes |

- `init!` → a 1-state relation (valid initial states); takes `pre`.
- `transition!` → a 2-state relation (`pre` → `post`).
- `readonly!` → a 2-state relation where the state cannot be modified (`pre === post`); exported as a transition.
- `property!` → a predicate on a single state; *not* exported as a transition. It exports useful facts from the state-machine view to thread-local reasoning as invokable lemmas on the `Instance`.

### The transition language

The transition DSL allows simple control flow (if-else, match, let-bindings) over four fundamental statements — `init`, `update`, `require`, `assert` — plus higher-level shorthands (`require let`, `assert let`, subscript/field update, and the collection commands `remove`/`have`/`add`/`deposit`/`guard`/`withdraw`). The grammar (verbatim):

```rust
TransitionStmt :=
   | TransitionStmt; TransitionStmt;
   | if $expr { TransitionStmt }
   | if $expr { TransitionStmt } else { TransitionStmt }
   | match $expr { ( $pat => { TransitionStmt } )* }
   | let $pat = $expr;
   | SingleStmt

SingleStmt :=
   | init $field_name = $expr;
   | update $field_name = $expr;
   | require $bool_expr;
   | assert $bool_expr (by { ... })? ;
   | require let $pat = $expr;
   | assert let $pat = $expr;
   | update $field_name ([sub_idx] | .subfield)* = $expr;
   | remove ... | have ... | add ... | deposit ... | guard ... | withdraw ...
```

Key distinction: `require` adds an *enabling condition* (the client must show it holds to perform the operation); `assert` declares a *safety condition* that Verus proves from the invariants and preceding `require`s. Clients may *assume* the `assert` holds whenever the transition is enabled — they do not need to prove it.

### Invariants and inductive proofs

An inductive invariant must satisfy `init(state) ==> inv(state)` and `transition(pre, post) && inv(pre) ==> inv(post)`. Invariant clauses are `#[invariant]`-annotated `&self` predicates; the macro conjoins them into a single `invariant`. You prove preservation with `#[inductive(name)]` lemmas (verbatim signatures):

```rust
// For an `init!` routine:
#[inductive(init_name)]
fn initialize_inductive(post: Self) {
    // Proof here
}

// For a `transition!` routine:
#[inductive(transition_name)]
fn transition_inductive(pre: Self, post: Self, n: int) {
    // Proof here
} 
```

The macro auto-generates the `requires`/`ensures`: for `init!`, `requires(init(post, ...))` / `ensures(post.invariant())`; for `transition!`, `requires(strong_transition(pre, post, ...) && pre.invariant())` / `ensures(post.invariant())`. The `strong` prefix means the proof may assume `assert` safety conditions in addition to `require`s.

## VerusSync and tokenization

A `tokenized_state_machine!` extends `state_machine!` by *sharding* each field into ghost **token types**. Any state of the system represents some collection of objects of those token types; transitions become **exchange functions** that consume a sub-collection of input tokens and produce a sub-collection of output tokens.

The high-level recipe (verbatim from `high-level-idea.md`):

1. Consider the program you want to verify.
2. Create an "abstraction" of the program as a tokenized state machine.
3. Verus will automatically produce for you a bunch of ghost "token types" that make up the tokenized state machine.
4. Implement a verified program using the token types.

### The `Instance` token and `constant` strategy

Every tokenized state machine generates a special `Instance` token type — a "unique identifier" for a given instantiation. All other token types carry an `instance: Instance` field, and every exchange requires all instance markers to match. `Instance` implements `Clone` (freely shareable). Fields with the `constant` strategy live *on* the `Instance` (accessed as `instance.field_name()`) and generate no separate token type.

### The PCM resource algebra

Underlying the token strategies is a **partial commutative monoid** (PCM) / resource algebra. `vstd/resource/pcm.rs` defines the `Resource<P: PCM>` tracked ghost object and the `PCM` trait (verbatim):

```rust
pub tracked struct Resource<P: PCM> {
    p: core::marker::PhantomData<P>,
}

pub trait PCM: ResourceAlgebra {
    spec fn unit() -> Self;
    proof fn op_unit(self)
        ensures Self::op(self, Self::unit()) == self;
    proof fn unit_valid()
        ensures Self::unit().valid();
}
```

`Resource` provides `alloc`, `join`/`split` (combine/divide via `P::op`), `validate`, and `update`/`update_nondeterministic` (frame-preserving updates). The strategy-reference doc formalizes each sharding strategy as a partial monoid with a composition `a · b` (well-defined when `a ## b`) and a "greater-than" relation `a >= b` (meaning `∃ c. a · c = b`, unique by *cancellativity*). The `monoid-formalism.md` doc gives the pen-and-paper justification constructing a global monoid `M = Unit | State(g1, g2, …) | Fail` from the per-field partial monoids.

### Tokenization strategies

Each field is annotated `#[sharding(strategy)]`. The strategies fall into three families.

**Variable-style** (exactly one token; manipulated with `init`/`update`):

| Strategy | Field type | Token value | Relationship |
|---|---|---|---|
| `variable` | `V` | `token![$instance => f => $value]` | exactly one token; value == field |
| `constant` | `V` | (on `Instance`) | `instance.field()`; never updated |

**Collection-style** (monoid-sharded; manipulated with `remove`/`have`/`add`):

| Strategy | Type | Token value | Relationship |
|---|---|---|---|
| `option` | `Option<V>` | `token![… => f => $v]` | no token for `None`, one for `Some(v)` |
| `map` | `Map<K, V>` | `token![… => f => $k => $v]` | at most one token per key |
| `multiset` | `Multiset<V>` | `token![… => f => $v]` | no restrictions |
| `set` | `Set<V>` | `token![… => f => $v]` | at most one token per value |
| `count` | `nat` | `token![… => f => $n]` | field value == sum of all token counts |
| `bool` | `bool` | `token![… => f => true]` | token exists ⟺ `true` |

The three collection commands mean (verbatim):

| Command | As transition | Exchange Fn Parameter |
|---|---|---|
| `remove f -= (x);` | `require f >= x;` / `update f = f - x;` | Input argument, consumed |
| `have f >= (x);` | `require f >= x;` | Input argument of type `&_` |
| `add f += (x);` | `assert f ## x;` / `update f = f · x;` | Output argument |

`add` uses `assert` (not `require`) because the output tokens do not exist before the transition — their existence cannot justify the transition; the developer must prove the *inherent safety condition* from the invariant. Singleton shorthands exist: `add f += Some(x)` (option), `add f += [k => v]` (map), `add f += {x}` (set/multiset).

**Persistent** variants (`persistent_option`, `persistent_map`, `persistent_set`, `persistent_count`, `persistent_bool`): state is permanent once introduced, so uniqueness constraints are dropped and tokens implement `Clone`. They are *not* cancellative, so `remove` is unavailable — only `have` and `add`.

**Storage** strategies (`storage_option`, `storage_map`): the instance can *store* tokens of an arbitrary token type `Tok`; clients "check out" and "check back in" tokens via `deposit`/`withdraw`/`guard`. This is the mechanism for transferring ownership of permission tokens (e.g. `PCell` `PointsTo`s) through a protocol. `guard` produces a shared `&Tok` reference.

**`not_tokenized`**: generates no token type; useful as an alternative to an existential invariant variable. Reading `pre.field` makes the operation nondeterministic, so it may only be accessed in a `birds_eye` context.

### The token traits (`vstd/tokens.rs`)

VerusSync-generated tokens implement traits in `vstd/tokens.rs`:

- `ValueToken<Value>` / `UniqueValueToken<Value>` — for `variable`, `option`, `persistent_option`. `agree` (all tokens for the same instance agree on value); `unique` (non-`Copy` variants: two tokens must be for distinct instances).
- `KeyValueToken<Key, Value>` / `UniqueKeyValueToken` — for `map`/`imap`/`persistent_map`. Each token is a single key-value pair.
- `CountToken` — for `count`. `join`/`split` combine/divide additively; `weaken_shared` produces a shared lower-bound reference.
- `MonotonicCountToken` (+ `Copy`) — for `persistent_count`. A lower bound that increases monotonically.
- `ElementToken<Element>` / `UniqueElementToken` — for `set`/`iset`/`persistent_set`/`multiset`. Each token is a single element.

`InstanceId` is `pub type InstanceId = super::resource::Loc;`.

### `birds_eye`

The `birds_eye` keyword (prefixed on a `let`) allows unrestricted reads of `pre` without impacting input/output tokens — useful for `not_tokenized` and storage fields. It makes operations potentially *nondeterministic*. Two restrictions: no precondition (`require`/`remove`/`have`/`deposit`) may depend on a `birds_eye` variable, and no `guard` may depend on one (crucial for soundness — the guarded `&Tok` must remain valid).

## Prophecy variables

`vstd/proph.rs` provides two forms of prophecy variables, with different tradeoffs:

- **`Prophecy<T: Structural>`** — resolves to an *exec*-computed value; `view()` is the prophecized value. Does *not* allow dependent resolutions; `view()` is (counterintuitively) *not* marked `#[verifier::prophetic]`, so it is not subject to prophecy-dependence restrictions.
- **`ProphecyGhost<T>`** — a `tracked` struct; `value()` is marked `#[verifier::prophetic]`. Allows ghost resolution *and* dependent resolutions (via `resolve_dependent`/`resolve_dependent_2`/`resolve_dependent_3`), but is subject to Verus's prophecy-dependence tracking.

The tradeoff table (verbatim):

| | Ghost resolution | Dependent resolution | Prophecy-dependence tracking |
|---|---|---|---|
| `Prophecy` | ✘ Exec only | ✘ Not allowed | ✔ No enforcement |
| `ProphecyGhost` | ✔ Allowed | ✔ Allowed | ✘ Enforced |

The two soundness issues these tradeoffs address: (1) cyclically dependent prophecies (`p.resolve(!p.value())` would be a contradiction — `ProphecyGhost`'s dependence tracking rejects it); (2) unbounded prophecies and termination checking (a `ProphecySeq` could make a `decreases` measure decrease forever — dependence tracking rejects the `decreases` clause). Verus also uses a prophecy-based encoding for mutable borrows, where `*final(x)` is prophetic and subject to dependence tracking.

`ProphecySeq<T>` (built on `ProphecyGhost<Seq<T>>`) supports resolving one element at a time via `resolve_cons`/`resolve_nil`.

## Teaching examples

### Counting to 2

The simplest concurrent example: a counter initialized to 0, two child threads each atomically increment it, the main thread joins and reads 2. The abstraction uses a chalkboard-and-tickets analogy: the counter is the chalkboard; each thread holds a ticket that, when "stamped" (used to increment), cannot be reused. The (incomplete) first attempt at a `tokenized_state_machine!` (verbatim from `counting-to-2.md`):

```rust
tokenized_state_machine!{
    X {
        fields {
            #[sharding(variable)]
            pub counter: int,

            #[sharding(variable)]
            pub ticket_a: bool,

            #[sharding(variable)]
            pub ticket_b: bool,
        }

        init!{
            initialize() {
                init counter = 0;                   // Initialize "chalkboard" to 0
                init ticket_a = false;              // Create one "unstamped ticket"
                init ticket_b = false;              // Create another "unstamped ticket"
            }
        }

        transition!{
            do_increment_a() {
                require(!pre.ticket_a);             // Require the client to provide an "unstamped ticket"
                update counter = pre.counter + 1;   // Increment the chalkboard counter by 1
                update ticket_a = true;             // Stamp the ticket
            }
        }

        transition!{
            do_increment_b() {
                require(!pre.ticket_b);             // Require the client to provide an "unstamped ticket"
                update counter = pre.counter + 1;   // Increment the chalkboard counter by 1
                update ticket_b = true;             // Stamp the ticket
            }
        }

        readonly!{
            finalize() {
                require(pre.ticket_a);              // Given that both tickets are stamped
                require(pre.ticket_b);              // ...
                assert(pre.counter == 2);           // one can conclude the chalkboard value is 2.
            }
        }
    }
}
```

Without an invariant, Verus rejects the `assert(pre.counter == 2)` safety condition. The invariant ties the counter to the number of stamped tickets. The generated exchange function for `do_increment_a` takes `&mut X::counter` and `&mut X::ticket_a` (both modified) and notably takes *no* `ticket_b` token at all — the transition doesn't depend on it. The implementation associates the `counter` field to an `atomic_ghost::AtomicU32<X::counter>`.

### Counting to n

Generalizing to `num_threads` threads introduces the `constant` strategy (for `num_threads`, stored on the `Instance`) and the `count` strategy (for the ticket fields). The key insight: tickets are a *count* of something (Alice's 3 + Bob's 2 = 5), unlike the chalkboard value (two chalkboards with 3 and 2 are just invalid). The `count` strategy makes the field value the *sum total* of all tokens, and `count` tokens are fungible via `join`/`split` (verbatim generated code):

```rust
#[proof]
#[verifier(unforgeable)]
pub struct unstamped_tickets {
    #[spec] pub instance: Instance,
    #[spec] pub value: nat,
}

impl unstamped_tickets {
    #[proof]
    #[verifier(returns(proof))]
    pub fn join(#[proof] self, #[proof] other: Self) -> Self {
        requires(equal(self.instance, other.instance));
        ensures(|s: Self| {
            equal(s.instance, self.instance)
                && equal(s.value, self.value + other.value)
        });
        // ...
    }

    #[proof]
    #[verifier(returns(proof))]
    pub fn split(#[proof] self, #[spec] i: nat) -> (Self, Self) {
        requires(i <= self.value);
        ensures(|s: (Self, Self)| {
             equal(s.0.instance, self.instance)
                && equal(s.1.instance, self.instance)
                && equal(s.0.value, i)
                && equal(s.1.value, self.value - i)
        });
        // ...
    }
}
```

Because `count` fields cannot be read/written arbitrarily (a client's tokens only establish a *lower bound* on the global value), transitions must use `remove`/`have`/`add` instead of `update`. The `tr_inc` transition exchanges one unstamped ticket for one stamped ticket (verbatim):

```rust
transition!{
    tr_inc() {
        // Replace a single unstamped ticket with a stamped ticket
        require(pre.unstamped_tickets >= 1); 
        update unstamped_tickets = pre.unstamped_tickets - 1;
        update stamped_tickets = pre.stamped_tickets + 1;

        assert(pre.counter < pre.num_threads);
        update counter = pre.counter + 1;
    }   
}
```

This must be rewritten with `remove`/`add` for the `count` fields. The `finalize` uses `have` (which does not consume) rather than `remove`, because the client only needs to *exhibit* enough stamped tickets, not destroy them.

### Producer-consumer queue

A single-producer, single-consumer ring buffer over `UnsafeCell<MaybeUninit<T>>` (verified alternative: `PCell<T>`). The central challenge: `PCell` operations are *non-atomic*, so the permission token cannot be held under an `AtomicInvariant` (which can only be open for one atomic step). Instead, the permission token is transferred at the four atomic operations (`produce_start`/`produce_end`/`consume_start`/`consume_end`). This uses the `storage_map` strategy: the instance *stores* all the `PCell` permission tokens, and the producer/consumer "check out" and "check back in" tokens. The `produce_start` transition `withdraw`s the permission (removing the key from the storage map); `produce_end` `deposit`s it back.

### Reference-counted smart pointer

An `Rc<T>`-like smart pointer verified with a `tokenized_state_machine!` defining `ref` and `counter` tokens, tied to the actual `u64` counter via a `LocalInvariant`. The tutorial (`rc.md`) is marked TODO beyond the field definitions — *(incomplete upstream)*.

## Runnable example

A minimal, self-contained `state_machine!` (non-tokenized) that Verus can verify. This is the `AdderMachine` example verbatim from the upstream guide, suitable for pasting into a `.rs` file under `verus!`:

```rust
use vstd::prelude::*;

verus! {

state_machine!{
    AdderMachine {
        fields {
            pub number: int,
        }

        init!{
            initialize() {
                init number = 0;
            }
        }

        transition!{
            add(n: int) {
                update number = pre.number + 2*n;
            }
        }

        #[invariant]
        pub fn is_even(&self) -> bool {
            self.number % 2 == 0
        }

        #[inductive(initialize)]
        fn initialize_inductive(post: Self) {
            // Verus proves that 0 % 2 == 0
        }

        #[inductive(add)]
        fn add_inductive(pre: Self, post: Self, n: int) {
            // Verus proves that if `pre.number % 2 == 0` then
            // `post.number` is `pre.number + 2*n` is divisible by 2 as well.
        }
    }
}

} // verus!
```

Run with:

```bash
verus path/to/adder_machine.rs
```

> **Caveat:** The `state_machine!` macro is provided by `verus_state_machines_macros`. The exact crate/import wiring for a standalone file may require a `Cargo.toml` with `vstd` as a dependency; see [getting-started.md](./getting-started.md). The tokenized variant `tokenized_state_machine!` additionally requires the `verus_state_machines_macros` crate. *(The upstream guide does not give a standalone runnable tokenized example; the counting-to-2 source is split across `{{#include}}` fragments.)*
