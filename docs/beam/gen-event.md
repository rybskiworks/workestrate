## Core guidance

### Event manager vs event handler

An *event manager* is a named object to which events can be sent. An *event*
can be an error, an alarm, or information to be logged. Zero, one, or many
*event handlers* are installed; when notified, the event is processed by all
installed handlers.

> "An event manager is implemented as a process and each event handler is
> implemented as a callback module."

> "The event manager essentially maintains a list of `{Module, State}` pairs,
> where each `Module` is an event handler, and `State` is the internal state of
> that event handler."

### Handlers share the manager's process — NO process isolation

The event manager is a single process. Each event handler is a callback module,
NOT a separate process. All installed handlers execute within the manager's
process, so there is NO process isolation between handlers — a crash or
long-running handler affects the whole manager. The manager maintains a list of
`{Module, State}` pairs. This is the central architectural fact of `gen_event`.

### Starting an event manager

- `gen_event:start_link/1` — spawns and links to a new event manager process.
  Use when part of a supervision tree.
- `gen_event:start/1` — standalone (not part of a supervision tree).
- Name arg: `{local, Name}` | `{global, Name}` | omitted (pid).

> "`gen_event:start_link/1` spawns and links to a new event manager process."

> "`gen_event:start_link/1` must be used if the event manager is part of a
> supervision tree, meaning that it was started by a supervisor. There is
> another function, `gen_event:start/1`, to start a standalone event manager
> that is not part of a supervision tree."

### Adding handlers

- `gen_event:add_handler(EventMgr, Module, Args)` — the manager calls
  `Module:init(Args)`. `Args` is the third argument. `init/1` must return
  `{ok, State}`. UNSUPERVISED — if the handler's callback fails, the handler is
  simply removed; no supervisor is informed.

> "The event manager calls the callback function `terminal_logger:init([])`,
> where the argument `[]` is the third argument to `add_handler`. `init/1` is
> expected to return `{ok, State}`, where `State` is the internal state of the
> event handler."

- `gen_event:add_sup_handler/3` — supervised variant. The event manager also
  supervises the connection by linking the event handler and the calling
  process. Two directions must be handled:
  - **Event handler deleted → calling process is notified.** If the event
    handler is deleted later, the event manager sends a message
    `{gen_event_EXIT, Handler, Reason}` to the calling process. `Reason` is
    one of:
    - `normal` — handler removed via `delete_handler/3` or a callback returned
      `remove_handler`.
    - `shutdown` — handler removed because the event manager is terminating.
    - `{swapped, NewHandler, Pid}` — process `Pid` replaced the handler with
      `NewHandler` via `swap_handler/3` or `swap_sup_handler/3`.
    - Other `term()` — handler removed because of an error (term depends on
      error).
  - **Calling process terminates → handler is deleted.** If the calling
    process later terminates with `Reason`, the event manager deletes any
    supervised event handlers by calling `Module:terminate/2`, then calls
    `Module:handle_info/2` for each remaining handler. So OTHER handlers on
    the manager should expect
    `Module:handle_info({'EXIT', Pid, Reason}, State)` callbacks.

> "the event manager also supervises the connection by linking the event
> handler and the calling process."

> "If the event handler is deleted later, the event manager sends a message
> {gen_event_EXIT,Handler,Reason} to the calling process."

### Notifying about events

- `gen_event:notify(EventMgr, Event)` — asynchronous. The event is made into a
  message and sent to the manager. On receipt, the manager calls
  `handle_event(Event, State)` for each installed handler in add-order.
  `handle_event/2` must return `{ok, State1}`.

> "The event is made into a message and sent to the event manager. When the
> event is received, the event manager calls `handle_event(Event, State)` for
> each installed event handler, in the same order as they were added. The
> function is expected to return a tuple `{ok,State1}`, where `State1` is a new
> value for the state of the event handler."

- `sync_notify/2` — synchronous variant. Crawl 35 now details it: it returns
  `ok` only after the event has been handled by all event handlers.

> "This function will return ok after the event has been handled by all event
> handlers."

### Calling a handler

- `gen_event:call/3` — synchronous call to a specific handler's
  `handle_call/2`. Crawl 35 now details the `handle_call/2` return shapes
  (see the expanded callback contract below). On failure, the call exits the
  calling process.

> "When this call fails it exits the calling process. The exit term is of the
> form {Reason, Location} where Location = {gen_event, call, ArgList}."

### Deleting a handler

- `gen_event:delete_handler(EventMgr, Module, Args)` — the manager calls
  `Module:terminate(Args, State)`. `Args` is the third argument. `terminate/2`
  is the opposite of `init/1` (cleanup); its return value is IGNORED.

> "The event manager calls the callback function
> `terminal_logger:terminate([], State)`, where the argument `[]` is the third
> argument to `delete_handler`. `terminate/2` is to be the opposite of `init/1`
> and do any necessary cleaning up. Its return value is ignored."

### Stopping the manager

- When stopped, each installed handler gets `terminate/2` called (same as
  deleting).
- In a supervision tree: no stop function needed; supervisor terminates it per
  its shutdown strategy.
- Standalone: `gen_event:stop(error_man)`.

> "When an event manager is stopped, it gives each of the installed event
> handlers the chance to clean up by calling `terminate/2`, the same way as
> when deleting a handler."

> "If the event manager is part of a supervision tree, no stop function is
> needed. The event manager is automatically terminated by its supervisor."

### The `gen_event` module API (crawl 35)

The behavior function -> callback mapping (verbatim table):
```
gen_event module                   Callback module
----------------                   ---------------
gen_event:start
gen_event:start_monitor
gen_event:start_link       ----->  -

gen_event:add_handler
gen_event:add_sup_handler  ----->  Module:init/1

gen_event:notify
gen_event:sync_notify      ----->  Module:handle_event/2

gen_event:send_request
gen_event:call             ----->  Module:handle_call/2

-                          ----->  Module:handle_info/2

gen_event:delete_handler   ----->  Module:terminate/2

gen_event:swap_handler
gen_event:swap_sup_handler ----->  Module1:terminate/2
                                   Module2:init/1

gen_event:which_handlers   ----->  -

gen_event:stop             ----->  Module:terminate/2

-                          ----->  Module:code_change/3
```

Key functions (exact arities):

- `start/0,1,2` and `start_link/0,1,2` (note `start/2`, `start_link/2` since
  OTP 20.0).
- `start_monitor/0,1,2` (since OTP 23.0) — returns `{ok, {Pid, Mon}}`
  (`start_mon_ret()`), NOT `{ok, Pid}`.
- `add_handler(EventMgrRef, Handler, Args)` — add handler, calls
  `Module:init/1`.
- `add_sup_handler(EventMgrRef, Handler, Args)` — supervised (links calling
  process).
- `swap_handler(EventMgrRef, OldHandler, NewHandler)` —
  `OldHandler/NewHandler :: {handler(), term()}`.
- `swap_sup_handler(EventMgrRef, OldHandler, NewHandler)` — swap + supervise
  NewHandler.
- `notify(EventMgrRef, Event) -> ok` — async.
- `sync_notify(EventMgrRef, Event) -> ok` — synchronous.

> "This function will return ok after the event has been handled by all event
> handlers."

- `call(EventMgrRef, Handler, Request)` ≡ `call(..., 5000)`;
  `call(EventMgrRef, Handler, Request, Timeout)`.

> "When this call fails it exits the calling process. The exit term is of the
> form {Reason, Location} where Location = {gen_event, call, ArgList}."

- `send_request/3,5`, `receive_response/2,3`, `wait_response/2,3`,
  `check_response/2,3` — async call API.
- `delete_handler(EventMgrRef, Handler, Args)` — calls `Module:terminate/2`;
  returns terminate's return value, or `{error, module_not_found}`.
- `which_handlers(EventMgrRef) -> [handler()]` — list all installed handlers.
- `stop(EventMgrRef)` ≡ `stop(EventMgrRef, normal, infinity)`;
  `stop(EventMgrRef, Reason, Timeout)` (since OTP 18.0).

> "Any other reason than normal, shutdown, or {shutdown, Term} causes an
> error report to be issued using logger."

Type aliases:

- `start_ret() :: {ok, pid()} | {error, term()}`
- `start_mon_ret() :: {ok, {pid(), reference()}} | {error, term()}`
- `add_handler_ret() :: ok | term() | {'EXIT', term()}`
- `del_handler_ret() :: ok | term() | {'EXIT', term()}`
- `handler() :: atom() | {atom(), Id :: term()}` (Module or `{Module, Id}`).

### Handler callback contract (return shapes)

Crawl 35 (the STDLIB `gen_event` module reference page) confirms and provides
these shapes verbatim as `-callback` definitions. The full contracts:

#### `init/1`
```
-callback init(InitArgs :: term()) ->
                  {ok, State :: term()} | {ok, State :: term(), hibernate} | {error, Reason :: term()}.
```
- `InitArgs` is the `Args` of `add_handler/3`/`add_sup_handler/3`, OR — for a
  swap — `{Args, Term}` where `Term` is the return value of the old handler's
  `terminate/2`.
- `{ok, State}` or `{ok, State, hibernate}` on success. `{ok, State, hibernate}`
  causes the event manager to hibernate via `proc_lib:hibernate/3`.

#### `handle_event/2`
```
-callback handle_event(Event :: term(), State :: term()) ->
                          {ok, NewState :: term()} |
                          {ok, NewState :: term(), hibernate} |
                          {swap_handler,
                           Args1 :: term(),
                           NewState :: term(),
                           Handler2 :: atom() | {atom(), Id :: term()},
                           Args2 :: term()} |
                          remove_handler.
```
- Called for each installed handler on `notify/2` / `sync_notify/2`.
- `{swap_handler, Args1, NewState, Handler2, Args2}`: handler replaced by
  `Handler2` via `Module:terminate(Args1, NewState)` then
  `Module2:init({Args2, Term})` where `Term` = terminate's return value.
- `remove_handler`: handler deleted via
  `Module:terminate(remove_handler, State)`.

#### `handle_call/2`
```
-callback handle_call(Request :: term(), State :: term()) ->
                         {ok, Reply :: term(), NewState :: term()} |
                         {ok, Reply :: term(), NewState :: term(), hibernate} |
                         {swap_handler,
                          Reply :: term(),
                          Args1 :: term(),
                          NewState :: term(),
                          Handler2 :: atom() | {atom(), Id :: term()},
                          Args2 :: term()} |
                         {remove_handler, Reply :: term()}.
```
- Same shapes as `handle_event/2` but each carries a `Reply` returned to the
  `call/3,4` client. `remove_handler` form here is `{remove_handler, Reply}`.

#### `handle_info/2` (optional)
```
-callback handle_info(Info :: term(), State :: term()) ->
                         {ok, NewState :: term()} |
                         {ok, NewState :: term(), hibernate} |
                         {swap_handler, Args1, NewState, Handler2, Args2} |
                         remove_handler.
```
- Called for non-event/non-request messages. In particular called when a
  process that called `add_sup_handler/3` terminates — expect
  `Module:handle_info({'EXIT', Pid, Reason}, State)`.
- Default implementation logs unexpected `Info` and returns `{ok, State}`.
- Note: the system doc page (crawl 09) showed `{noreply, State1}` in its
  `handle_info` example; the module ref (crawl 35) uses `{ok, NewState}` and
  is authoritative.

#### `terminate/2` (optional)
```
-callback terminate(Args ::
                        term() |
                        {stop, Reason :: term()} |
                        stop | remove_handler |
                        {error, {'EXIT', Reason :: term()}} |
                        {error, term()},
                    State :: term()) ->
                       term().
```
- `Args` semantics:
  - the `Args` of `delete_handler/3`/`swap_handler/3`/`swap_sup_handler/3`;
  - `{stop, Reason}` if supervised connection to a process that terminated
    with `Reason`;
  - `stop` if the event manager is terminating;
  - `remove_handler` if another callback returned `remove_handler` /
    `{remove_handler, Reply}`;
  - `{error, Term}` if a callback returned an unexpected value `Term`;
  - `{error, {'EXIT', Reason}}` if a callback failed.
- Return value: becomes `delete_handler/3`'s return value; passed to new
  handler's `init/1` on swap; otherwise ignored. Default impl does no cleanup.

#### `code_change/3` (optional)
```
-callback code_change(OldVsn :: term() | {down, term()}, State :: term(), Extra :: term()) ->
                         {ok, NewState :: term()}.
```
- Called on release upgrade/downgrade with `{update, Module, Change, ...}`
  in appup. `OldVsn = Vsn` (upgrade) or `{down, Vsn}` (downgrade). If no `vsn`
  attribute, version = Beam file checksum. `Extra` from `{advanced, Extra}`.
- If `{advanced, Extra}` is specified but `code_change/3` is not implemented,
  the handler crashes with `undef`.

#### `format_status/1,2` (optional, since OTP 25.0)
For `sys` status formatting; not detailed in extraction scope.

### Handler termination

`terminate/2` is called when a handler is deleted, when the manager stops, or
when a handler callback returns `remove_handler`. It must undo `init/1` (close
files, etc.). Return value is ignored.

### Handling other messages

> "If the `gen_event` process is to be able to receive other messages than
> events, the callback function `handle_info(Info, State)` must be implemented
> to handle them. Examples of other messages are exit messages if the event
> manager is linked to other processes than the supervisor (for example via
> `gen_event:add_sup_handler/3`) and is trapping exit signals."

### No native `get_state` for managers — introspection via `sys:get_status/1`

CORRECTION: `gen_event` does NOT expose a `get_state` function for managers
(unlike `gen_server`). Introspection of manager state is via
`sys:get_status/1` (referenced in the module ref's See Also), not a
`gen_event`-native `get_state`.

> "there is NO `get_state` function for gen_event managers on this page.
> gen_event does not expose `get_state`/`get_state` like gen_server.
> Introspection of manager state is via `sys:get_status/1`."

See the `proc-lib-and-sys` doc for `sys` tooling.

### Manager resilience and hibernation (crawl 35)

Strict rules from crawl 35:

- `gen_event` is more tolerant of callback errors than other behaviours: if a
  callback function for an installed event handler fails with `Reason`, or
  returns a bad value `Term`, the event manager does NOT fail. It deletes only
  that handler by calling `Module:terminate/2` with `{error, {'EXIT', Reason}}`
  or `{error, Term}`, respectively. No other event handler is affected.

> "If a callback function for an installed event handler fails with Reason, or
> returns a bad value Term, the event manager does not fail. It deletes the
> event handler by calling callback function Module:terminate/2, giving as
> argument {error, {'EXIT', Reason}} or {error, Term}, respectively. No other
> event handler is affected."

- The manager traps exit signals automatically.

> "Notice that an event manager does trap exit signals automatically."

- Hibernation: if ANY handler returns `{ok, NewState, hibernate}` (or `init`
  returns `{ok, State, hibernate}`), the WHOLE manager hibernates via
  `proc_lib:hibernate/3`. Hibernation costs >= 2 GCs; avoid for busy managers.

> "Notice that when multiple event handlers are invoked, it is sufficient that
> one single event handler returns a hibernate request for the whole event
> manager to go into hibernation."

- `notify/2` does not fail even if the manager does not exist, UNLESS the
  manager is specified as a `Name` (registered name).
- Distributed signaling: blocking signaling over distribution can
  significantly delay `call` timeouts.

## Practical rules

1. Use `gen_event:start_link/1` when part of a supervision tree; `start/1`
   standalone.
2. `init/1` MUST return `{ok, State}`.
3. `handle_event/2` MUST return `{ok, State1}`.
4. `terminate/2` is the opposite of `init/1` (cleanup); return value IGNORED.
5. Handlers are invoked in the same order they were added.
6. In a supervision tree, no stop function is needed — the supervisor
   terminates the manager per its shutdown strategy.
7. Implement `handle_info/2` for non-event messages (EXIT messages via
   `add_sup_handler/3` when trapping exits).
8. Implement `code_change/3` for hot code upgrade.
9. Handlers share the manager's process — NO process isolation; a crash or
   long-running handler affects the whole manager.
10. `add_handler/3` = unsupervised; `add_sup_handler/3` = supervised (EXIT
    message to caller on callback-failure removal).
11. Use `notify/2` for asynchronous events. `sync_notify/2` semantics defer to
    the module ref (not in crawl 09).
12. Use `delete_handler/3` to remove a handler; manager calls
    `Module:terminate(Args, State)`.
13. `swap_handler/3` transfers state from OldHandler to NewHandler via
    `terminate`'s return value passed to `init({Args2, Term})`.
14. `which_handlers/1` lists all installed handlers as `[handler()]`.
15. `stop/3` with a non-normal/shutdown reason issues a logger error report.
16. `{ok, State, hibernate}` from any handler hibernates the WHOLE manager
    (cost >= 2 GCs); avoid for busy managers.
17. A callback crash/bad-value deletes ONLY that handler; the manager
    survives.

## Review checklist

- [ ] Manager started with `start_link/1` (supervision tree) or `start/1`
      (standalone) as appropriate; name arg is `{local, Name}`,
      `{global, Name}`, or omitted (pid).
- [ ] `init/1` returns `{ok, State}`; `handle_event/2` returns `{ok, State1}`;
      `terminate/2` cleans up and its (ignored) return value is not relied
      upon.
- [ ] `add_handler/3` vs `add_sup_handler/3` chosen correctly; `add_sup_handler/3`
      callers handle EXIT messages in `handle_info/2` when trapping exits and
      linked to other processes.
- [ ] `handle_info/2` implemented for non-event messages.
- [ ] `code_change/3` implemented for hot code upgrade.
- [ ] No assumption of process isolation between handlers; blocking work
      flagged; handler invocation order (add-order) understood.
- [ ] If using `add_sup_handler/3`, the calling process handles
      `{gen_event_EXIT, Handler, Reason}` messages.
- [ ] No assumption that gen_event managers expose `get_state`; use
      `sys:get_status/1` for introspection.
- [ ] Hibernation (`{ok, State, hibernate}`) understood to affect the WHOLE
      manager.

## Implementation checklist

- [ ] Start with `gen_event:start_link/1` under a supervisor, or `start/1`
      standalone; choose name form `{local, Name}` / `{global, Name}` / omitted.
- [ ] Handler module exports `init/1`, `handle_event/2`, `terminate/2`, and
      (as needed) `handle_call/2`, `handle_info/2`, `code_change/3`.
- [ ] `init/1` returns `{ok, State}`; `handle_event/2` returns `{ok, State1}`;
      `terminate/2` undoes `init/1` (return value ignored).
- [ ] `add_handler/3` for unsupervised; `add_sup_handler/3` when caller must be
      informed of removal via EXIT.
- [ ] `handle_info/2` handles `{'EXIT', Pid, Reason}` when trapping exits and
      linked to other processes; `code_change/3` returns `{ok, NewState}`.
- [ ] `notify/2` for events; `delete_handler/3` to remove; stop standalone
      managers with `gen_event:stop/1` (supervised managers terminated by
      their supervisor).
- [ ] `swap_handler/3` / `swap_sup_handler/3` used for atomic handler
      replacement (state transfer via terminate→init).
- [ ] `which_handlers/1` used to inspect installed handlers.
- [ ] `stop/3` reason chosen to avoid spurious logger error reports
      (normal/shutdown/{shutdown,Term}).

## Runtime / debugging checklist

- [ ] Confirm manager process alive and registered as expected.
- [ ] Confirm whether handlers were added with `add_handler/3` or
      `add_sup_handler/3` (affects EXIT-on-removal behavior).
- [ ] Check whether a handler was removed due to callback failure
      (unsupervised: silently removed; supervised: EXIT to caller).
- [ ] Check whether `handle_info/2` is implemented for non-event / EXIT
      messages when trapping exits.
- [ ] Check whether a handler is blocking the whole manager (no process
      isolation between handlers).
- [ ] Verify `terminate/2` ran for deleted handlers and on manager stop.
- [ ] Supervised managers: supervisor's shutdown strategy terminates the
      manager (no manual stop); standalone: `gen_event:stop/1` used.
- [ ] `sys:get_status/1` for manager introspection (gen_event has NO native
      `get_state` for managers).
- [ ] `gen_event:which_handlers/1` to list installed handlers.

## Examples

### `terminal_logger` — writes error messages to the terminal

```erlang
-module(terminal_logger).
-behaviour(gen_event).
-export([init/1, handle_event/2, terminate/2]).

init(_Args) ->
    {ok, []}.

handle_event(ErrorMsg, State) ->
    io:format("***Error*** ~p~n", [ErrorMsg]),
    {ok, State}.

terminate(_Args, _State) ->
    ok.
```

### `file_logger` — writes error messages to a file (state holds the file descriptor)

```erlang
-module(file_logger).
-behaviour(gen_event).
-export([init/1, handle_event/2, terminate/2]).

init(File) ->
    {ok, Fd} = file:open(File, read),
    {ok, Fd}.

handle_event(ErrorMsg, Fd) ->
    io:format(Fd, "***Error*** ~p~n", [ErrorMsg]),
    {ok, Fd}.

terminate(_Args, Fd) ->
    file:close(Fd).
```

### Shell session

```text
1> gen_event:start({local, error_man}).
{ok,<0.31.0>}
2> gen_event:add_handler(error_man, terminal_logger, []).
ok
3> gen_event:notify(error_man, no_reply).
***Error*** no_reply
ok
4> gen_event:delete_handler(error_man, terminal_logger, []).
ok
```

## Common mistakes

1. **Assuming handlers are isolated processes.** They share the manager's process; NO process isolation; a crash or long-running handler affects the whole manager.
2. **Using `start/1` for a supervised manager.** Use `start_link/1` when started by a supervisor.
3. **Returning other than `{ok, State}` from `init/1`.** MUST return `{ok, State}`.
4. **Returning other than `{ok, State1}` from `handle_event/2`.** MUST return `{ok, State1}` (other variants live on the module ref page).
5. **Relying on `terminate/2`'s return value.** It is IGNORED.
6. **Not implementing `handle_info/2` for non-event / EXIT messages.** Required for EXIT messages from `add_sup_handler/3` when trapping exits.
7. **Not implementing `code_change/3`.** Required for hot code upgrade.
8. **Expecting a supervised manager to need a manual stop.** In a supervision tree, no stop function is needed.
9. **Using `add_handler/3` when the caller must know about removal.** Use `add_sup_handler/3` for EXIT-on-removal.
10. **Forgetting handlers are invoked in add-order.**
11. **Expecting a plain `{'EXIT', Pid, Reason}` (not
    `{gen_event_EXIT, Handler, Reason}`) when a supervised handler is
    deleted.** The message to the calling process is
    `{gen_event_EXIT, Handler, Reason}`.
12. **Calling `gen_event:get_state/1` (does not exist for managers).** Use
    `sys:get_status/1`.
13. **Returning `{ok, State, hibernate}` from one handler and not realizing
    it hibernates the WHOLE manager.**
14. **Assuming a handler callback crash kills the manager.** It deletes only
    that handler; the manager survives.

## Strict vs contextual guidance

### Strict

Hard constraints from OTP semantics per crawl 09. Violations are bugs.

- `init/1` MUST return `{ok, State}`.
- `handle_event/2` MUST return `{ok, State1}`.
- `terminate/2` return value is IGNORED.
- Handlers are invoked in the same order they were added.
- `gen_event:start_link/1` for supervision tree; `gen_event:start/1`
  standalone.
- In a supervision tree, no stop function is needed — the supervisor
  terminates the manager per its shutdown strategy.
- `handle_info/2` must be implemented for non-event messages (EXIT messages
  via `add_sup_handler/3` when trapping exits).
- `code_change/3` must be implemented for hot code upgrade.
- Handlers share the manager's process — NO process isolation between
  handlers; a crash or long-running handler affects the whole manager.
- A handler callback crash/bad-value deletes ONLY that handler; the manager
  does NOT fail.
- The manager traps exit signals automatically.
- One handler's hibernate request hibernates the WHOLE manager.
- `notify/2` does not fail unless the manager is a registered `Name`.

### Contextual

- `add_handler/3` (unsupervised) vs `add_sup_handler/3` (supervised, EXIT to
  caller on removal).
- Manager naming: `{local, Name}`, `{global, Name}`, or omitted (pid).
- Whether `handle_call/2` is needed (for `gen_event:call/3`); return shapes
  are on the module ref page, not crawl 09.
- `swap_handler/3` vs `swap_sup_handler/3` (the latter supervises the new
  handler).
- `start_monitor/0,1,2` (returns `{ok, {Pid, Mon}}`) vs `start_link/0,1,2`
  (returns `{ok, Pid}`).

## Policy decisions for individual repos

1. **Manager start mode.** Must managers use `start_link/1` under a supervisor,
   or is `start/1` standalone permitted?
2. **Manager naming.** `{local, Name}`, `{global, Name}`, or unnamed (pid)?
3. **Handler supervision.** Must handlers use `add_sup_handler/3` (EXIT on
   removal), or is `add_handler/3` acceptable for stateless observers?
4. **`handle_info/2` policy.** Must every handler implement it, or only
   handlers installed via `add_sup_handler/3`?
5. **`code_change/3` policy.** Must every handler implement it, or only
   handlers whose state format may evolve?
6. **`sync_notify/2` / `call/3` policy.** Since crawl 09 defers these to the
   module ref, where is the authoritative reference, and are they permitted?
7. **Blocking handler policy.** Given no process isolation, is blocking work
   in `handle_event/2` banned, or allowed with documentation?
8. **Handler restoration on manager restart.** If a supervised manager
   restarts, who reinstalls the handlers?
