## Purpose

Defines Erlang's error terminology, the three exception classes (`error`, `exit`, `throw`), how each is raised and caught, the structure of the call-stack backtrace (stacktrace), and the canonical set of run-time error exit reasons. It is the reference_manual "Errors and Error Handling" chapter. It explicitly defers inter-process error handling (exit signals, links, monitors, `trap_exit`, `DOWN`) to the Processes chapter (`ref_man_processes.html`).

## Key concepts

- **Four error types (terminology):** compile-time errors, logical errors, run-time errors, generated errors.
  - Run-time errors → exception class `error` (e.g. `1+a`, or a call to `error/1`).
  - Generated errors → exception class `exit` (via `exit/1`) or `throw` (via `throw/1`).
- **Three exception classes** (Table: Exception Classes):
  - `error` — run-time error, e.g. `1+a`, or the process called `error/1`.
  - `exit` — the process called `exit/1`.
  - `throw` — the process called `throw/1`.
  - All three can also be generated by `erlang:raise/3`.
- **try vs catch:** `try` can distinguish between the classes; `catch` cannot. Both are described in the Expressions chapter.
- **Exception structure:** an exception consists of its class, an exit reason (see Exit Reason), and a stack trace.
- **Failure / termination:** when an exception occurs, the evaluating process is stopped ("fails"/"terminates"/"exits"). A process can also terminate for non-failure reasons. A terminating process emits an exit signal with an exit reason.
- **Stacktrace** = list of `{Module, Function, Arity, ExtraInfo}` and/or `{Fun, Arity, ExtraInfo}` tuples. `Arity` may be the argument list instead of an integer. `ExtraInfo` is a (possibly empty) list of 2-tuples; possible first-element atoms: `error_info`, `file`, `line`.
- **Exit reasons for class `error`:** the exit reason is a tuple `{Reason, Stack}` where `Reason` is one of the documented atoms/tuples (badarg, badarith, {badmatch,V}, function_clause, {case_clause,V}, if_clause, {try_clause,V}, undef, {badfun,F}, {badarity,{Fun,Args}}, timeout_value, noproc, noconnection, {nocatch,V}, system_limit).

## Strict rules / invariants

- **Stacktrace is for debugging only.** Tail-call optimization does not add new entries; stacktraces are depth-limited; compiler options/optimizations/future changes may add or remove entries. Code relying on stacktrace order/content may fail.
- **Sole guaranteed stacktrace invariant:** for class `error` with reason `undef`, the first stacktrace entry is guaranteed to be `{Module, Function, Arity}` of the attempted function.
- **`try` distinguishes exception classes; `catch` does not.**
- **`error/3`** creates the `error_info` extra-info entry used by `erl_error:format_exception/4`.
- **`erlang:raise/3`** can generate any of the three classes.
- **Exit reason shape for run-time errors:** `{Reason, Stack}` (a 2-tuple), not a bare atom.
- **`{nocatch,V}`** is raised when a `throw` is evaluated outside the scope of a `catch` or `try`/`catch`; `V` is the thrown term.
- Inter-process exit-signal propagation, `trap_exit`, `DOWN`, link/monitor semantics are NOT defined here — they live in `ref_man_processes.html`.

## Examples

```erlang
%% Stacktrace bound from a catch (class error):
> {'EXIT',{test,Stacktrace}} = (catch error(test)), Stacktrace.
[{shell,apply_fun,3,[]},
 {erl_eval,do_apply,6,[]},
 ...]

%% Stacktrace bound from a try (any class; here throw):
> try throw(test) catch Class:Reason:Stacktrace -> Stacktrace end.
[{shell,apply_fun,3,[]},
 {erl_eval,do_apply,6,[]},
 ...]
```

## Behaviour / callback details

### Three exception classes and how each is raised/caught

| Class  | Raised by                                                                 | Caught by                       |
|--------|---------------------------------------------------------------------------|---------------------------------|
| `error` | a run-time error (e.g. `1+a`), or an explicit call to `error/1` (or `error/3` for extra info) | `try ... catch error:...` (class-distinguishable); also `catch` (yields `{'EXIT',{Reason,Stack}}`) |
| `exit`  | an explicit call to `exit/1`                                              | `try ... catch exit:...`; also `catch` |
| `throw` | an explicit call to `throw/1`                                             | `try ... catch throw:...`; also `catch` (but a `throw` outside any `catch`/`try` becomes `{nocatch,V}`) |

- All three classes can additionally be generated by `erlang:raise/3`.
- `try` can distinguish the class; `catch` cannot (it always yields `{'EXIT', {Reason, Stack}}` for class `error`, and the thrown/exit term otherwise).

### erlang:raise/3

- `erlang:raise/3` can raise any of the three classes (`error`, `exit`, `throw`). The page states this but does not give its argument signature here (see `../apps/erts/erlang.html#raise/3`).

### Exit reasons: normal / kill / shutdown / {shutdown,Term}

- **NOT covered on this page.** This page documents only the run-time-error reason atoms (badarg, badarith, etc.) and the `{Reason, Stack}` shape for class `error`.
- The reasons `normal`, `kill`, `shutdown`, and `{shutdown, Term}` belong to process termination / exit-signal semantics, which this page defers to `ref_man_processes.html` (Process Termination). The exit-reason → signal-behavior table is NOT present here.

### Exit signal propagation; links vs monitors; trap_exit; DOWN

- **NOT covered on this page.** The page only states that "A process that terminates emits an exit signal with an exit reason" and points to `ref_man_processes.html#process-termination` and `ref_man_processes.html#errors` for the inter-process machinery (links, monitors, `trap_exit` reception rules, `DOWN` messages). `link/1` and `monitor/2` are referenced only as the primitives that raise `noproc`/`noconnection`.

### Stacktrace semantics

- Stacktrace = list of `{Module, Function, Arity, ExtraInfo}` and/or `{Fun, Arity, ExtraInfo}`.
- `Arity` field may be the argument list instead of an arity integer, depending on the exception.
- `ExtraInfo` is a (possibly empty) list of 2-tuples; recognized keys: `error_info` (map, from `error/3`, consumed by `erl_error:format_exception/4`), `file` (source filename string), `line` (integer > 0).
- Bindable from a `try` for any class (`catch Class:Reason:Stacktrace`), or as part of the exit reason when a run-time error is caught by `catch` (`{'EXIT',{Reason,Stack}}`).
- Debug-only; tail-call optimization and depth limits apply. Only `undef` class-`error` first entry is guaranteed.

### exit/1 vs exit/2 (and exit_signal/2 if present)

- **`exit/1`** is covered: it is the generator of exception class `exit` (one of the three exception classes; see Exception Classes table). Calling `exit/1` raises an exception of class `exit` catchable by `try`/`catch`.
- **`exit/2`** is **NOT documented on this page.** The page links only to `../apps/erts/erlang.html#exit/1`. The two-argument `exit/2` (which sends an exit signal to a process rather than raising a local exception) belongs to the erts `erlang` module reference, not this chapter. There is no `exit_signal/2` BIF mentioned on this page.

## Verbatim quotes

1. **Terminology** — "Errors can roughly be divided into four different types:" … "Run-time errors - When a crash occurs. An example is when an operator is applied to arguments of the wrong type. The Erlang programming language has built-in features for handling of run-time errors. A run-time error can also be emulated by calling `error(Reason)`. Run-time errors are exceptions of class `error`." … "Generated errors - When the code itself calls `exit/1` or `throw/1`. Generated errors are exceptions of class `exit` or `throw`."

2. **Terminology (failure/exit signal)** — "When an exception occurs in Erlang, execution of the process that evaluated the erroneous expression is stopped. This is referred to as a failure, that execution or evaluation fails, or that the process fails, terminates, or exits. Notice that a process can terminate/exit for reasons other than a failure." … "A process that terminates emits an exit signal with an exit reason that describes why the process terminated."

3. **Exceptions** — "Exceptions are run-time errors or generated errors and are of three different classes, with different origins. The `try` expression can distinguish between the different classes, whereas the `catch` expression cannot."

4. **Exception Classes table** — "`error` — Run-time error, for example, `1+a`, or the process called `error/1`"; "`exit` — The process called `exit/1`"; "`throw` — The process called `throw/1`".

5. **Exceptions (raise/3)** — "All of the above exceptions can also be generated by calling `erlang:raise/3`."

6. **Exceptions (structure)** — "An exception consists of its class, an exit reason (see Exit Reason), and a stack trace (which aids in finding the code location of the exception)."

7. **The call-stack backtrace (stacktrace)** — "The stack backtrace (stacktrace) is a list that contains `{Module, Function, Arity, ExtraInfo}` and/or `{Fun, Arity, ExtraInfo}` tuples. The field `Arity` in the tuple can be the argument list of that function call instead of an arity integer, depending on the exception."

8. **The call-stack backtrace (warning)** — "Developers should rely on stacktrace entries only for debugging purposes." … "The only exception to this rule is the class `error` with the reason `undef` which is guaranteed to include the `Module`, `Function`, and `Arity` of the attempted function as the first stacktrace entry."

9. **Error Handling Between Processes** — "Processes can monitor other processes and detect process terminations, see Processes."

10. **Exit Reasons** — "When a run-time error occurs, that is an exception of class `error`. The exit reason is a tuple `{Reason,Stack}`, where `Reason` is a term indicating the type of error:" (followed by the badarg/badarith/.../system_limit list).

11. **Exit Reasons (Stack)** — "`Stack` is the stack of function calls being evaluated when the error occurred, given as a list of tuples `{Module,Name,Arity,ExtraInfo}` with the most recent function call first. The most recent function call tuple can in some cases be `{Module,Name,[Arg],ExtraInfo}`."
