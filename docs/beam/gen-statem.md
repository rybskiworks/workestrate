# gen_statem Behaviour

## Purpose

Source-verified guidance for the `gen_statem` behaviour in Erlang/OTP `stdlib`
(OTP 29.0.2 / stdlib v8.0.1). `gen_statem` is the generic state machine
behaviour that, since Erlang/OTP 20.0, replaces its predecessor `gen_fsm` and
"should be used for new code" (crawl 12, Purpose). It is an Event-Driven Mealy
state machine: events drive state transitions and actions are part of the model.
A `gen_statem` keeps a server `Data` item besides the state; because of this
data item and the absence of restrictions on the number of states or distinct
input events, a `gen_statem` machine is Turing complete, but "it feels mostly
like an Event-Driven Mealy machine" (crawl 04, Verbatim quote 1).

This document is BEAM-common and Erlang-native. No Elixir/Gleam syntax.

## Core guidance

### What `gen_statem` is

From crawl 12 (Purpose): "Generic state machine behaviour. Since Erlang/OTP
20.0 replaces its predecessor `gen_fsm`, and should be used for new code. A
`gen_statem` is a generic state machine server process with a standard set of
interface functions, tracing and error reporting, and fits into an OTP
supervision tree."

Features beyond `gen_fsm` (crawl 12, Purpose): "co-located state code,
arbitrary term state, event postponing, self-generated events, state time-out,
multiple generic named time-outs, absolute time-out time, automatic state enter
calls, reply from other state than the request (traceable with sys), multiple
replies, changing the callback module."

### When to use `gen_statem` over `gen_server`

From crawl 04 (Verbatim quote 2, "When to use gen_statem"): "You should
consider using gen_statem over gen_server if your process logic is convenient
to describe as a state machine and you need any of these gen_statem key
features: Co-located callback code for each state, for all event types, such as
call, cast, and info; Postponing events - a substitute for selective receive;
Inserted events - events from the state machine to itself; for purely internal
events in particular; State enter calls - callback on state entry co-located
with the rest of each state's callback code; Easy-to-use time-outs - state
time-outs, event time-outs, and generic time-outs (named time-outs)."

For simple state machines not needing these features, `gen_server` is fine:
smaller call overhead, "~2 vs 3.3 microseconds roundtrip" (crawl 04, Purpose).

### Callback modes

Two callback modes, selected by the return value of the mandatory
`Module:callback_mode/0` (crawl 12, "Callback modes & signatures (exact)"):

- `state_functions` — "state must be an atom (`state_name/0`); one callback
  function per state `Module:StateName/3` is used. (gen_fsm-like.)"
- `handle_event_function` — "state can be any term; the single callback
  `Module:handle_event/4` is used for all states."

From crawl 04 (Verbatim quote 3, "Callback Modes"): "The gen_statem behaviour
supports two callback modes: state_functions - Events are handled by one
callback function per state. handle_event_function - Events are handled by one
single callback function."

`callback_mode/0` is called when starting the gen_statem, after code change,
and after changing the callback module via `change_callback_module`,
`push_callback_module`, `pop_callback_module`. The result is cached (crawl 12).

### State enter mode

`state_enter` is the atom added to the `callback_mode/0` return list to enable
state enter calls (crawl 12, "StateEnter mode"). At every state change
(`NextState =/= CurrentState`) the engine calls the state callback with
arguments `(enter, OldState, Data)` or `(enter, OldState, State, Data)`
depending on callback mode. A state enter call is also done right before
entering the initial state (then `OldState =:= State`). A state enter call may
be repeated without a state change by returning `repeat_state` /
`repeat_state_and_data`. `code_change/4` state transform is a state rename,
not a state change (no enter call).

From crawl 04 (Verbatim quote 4, "Callback Modes"): "The Module:callback_mode()
function may also return a list containing the callback mode and the atom
state_enter in which case state enter calls are activated for the callback
mode."

### Event types (complete list)

From crawl 04 (Verbatim quote 9, "Event Types and Event Content"): "The
following is a complete list of event types and from where they come: cast ...
{call, From} ... info ... state_timeout ... {timeout, Name} ... timeout ...
internal - Generated by transition action {next_event, internal,
EventContent}. All event types above can also be generated using the next_event
action: {next_event, EventType, EventContent}."

| Event type        | Origin |
|-------------------|--------|
| `cast`            | `gen_statem:cast(ServerRef, Msg)`; `Msg` is `EventContent` |
| `{call, From}`    | `gen_statem:call/2`, `send_request/2`, `send_request/4`; `Request` is `EventContent`; `From` used via `{reply, From, Reply}` or `gen_statem:reply(From, Reply)` |
| `info`            | any regular process message; the message is `EventContent` |
| `state_timeout`   | from transition action `{state_timeout, Time, EventContent}` when the time-out expires |
| `{timeout, Name}` | from transition action `{{timeout, Name}, Time, EventContent}` when the generic time-out expires |
| `timeout`         | from transition action `{timeout, Time, EventContent}` (or short form `Time`) when the event time-out expires |
| `internal`        | only from transition action `{next_event, internal, EventContent}`; cannot come from an external source |

From crawl 04 (Verbatim quote 16, "Inserted Events"): "the internal type can
only be generated through action next_event. Hence, it cannot come from an
external source, so you can be certain that an internal event is an event from
your state machine to itself."

### Three timeout kinds

From crawl 04 (Verbatim quote 11, "Time-Outs"): "There are 3 types of
time-outs in gen_statem: state_timeout - There is one state time-out that is
automatically canceled by a state change. {timeout, Name} - There are any
number of generic time-outs differing by their Name. They have no automatic
canceling. timeout - There is one event time-out that is automatically canceled
by any event. Note that postponed and inserted events cancel this time-out just
as external events do."

Table mapping timeout kind → setting action → event type generated (crawl 12,
"Timeouts"):

| Timeout kind    | Setting action                                              | Event type generated |
|-----------------|-------------------------------------------------------------|----------------------|
| Event timeout   | `{timeout, Time, EventContent [, Opts]}` (or bare `Time`)  | `timeout`            |
| Generic (named) | `{{timeout, Name}, Time, EventContent [, Opts]}` (since OTP 20.0) | `{timeout, Name}` |
| State timeout   | `{state_timeout, Time, EventContent [, Opts]}` (since OTP 19.3) | `state_timeout`  |

### Common timeout semantics

From crawl 04 (Verbatim quote 12, "Time-Outs"): "When a time-out is started,
any running time-out of the same type (state_timeout, {timeout, Name}, or
timeout) is canceled, that is, the time-out is restarted with the new time and
event content. All time-outs have an EventContent that is part of the
transition action that starts the time-out. Different EventContent s do not
create different time-outs."

- `infinity` time: optimized by not starting; any running same-tag time-out is
  canceled; `EventContent` ignored (set to `undefined`).
- Explicit cancel: `{TimeoutType, cancel}`.
- Update while running: `{TimeoutType, update, NewEventContent}`; if no such
  time-out running, a time-out event is immediately delivered as a zero
  time-out.
- Zero time (`0`): not started; the time-out event is inserted to be processed
  after any events already enqueued and before any not-yet-received external
  events.

From crawl 04 (Verbatim quote 13, "Zero Time-Out"): "If a time-out is started
with the time 0 it will actually not be started. Instead the time-out event
will immediately be inserted to be processed after any events already enqueued,
and before any not yet received external events."

From crawl 12 (Verbatim quotes): "The behaviour of a time-out zero (a time-out
with time 0) differs subtly from Erlang's `receive ... after 0 ... end`. The
latter receives one message if there is one, while using the `timeout_action/0`
`{timeout, 0}` does not receive any external event. `gen_server`'s time-out
works like Erlang's `receive ... after 0 ... end`, in contrast to
`gen_statem`."

### Actions list (transition actions)

From crawl 04 ("Actions list"):

- `{postpone, Boolean}` — if `true`, postpone the current event.
- `{hibernate, Boolean}` — if `true`, hibernate the gen_statem.
- `{state_timeout, Time, EventContent [, Opts]}` | `{state_timeout, update, EventContent}` | `{state_timeout, cancel}` — start/update/cancel a state time-out.
- `{{timeout, Name}, Time, EventContent [, Opts]}` | `{{timeout, Name}, update, EventContent}` | `{{timeout, Name}, cancel}` — start/update/cancel a generic time-out.
- `{timeout, Time, EventContent [, Opts]}` — start an event time-out.
- `{reply, From, Reply}` — reply to a caller (the only immediate action).
- `{next_event, EventType, EventContent}` — generate the next event to handle (inserted events).
- `{change_callback_module, NewModule}` — change callback module for the running server (during any state transition, not from a state enter call).
- `{push_callback_module, NewModule}` — push current module to an internal stack and set new module.
- `pop_callback_module` — pop top module from the stack and set it as new module (fails if stack empty).

From crawl 04 (Verbatim quote 8, "Transition Actions"): "Out of these
transition actions, the only immediate action is reply for replying to a
caller. The other actions are collected and handled later during the state
transition. Inserted events are stored and inserted all together, and the rest
set transition options where the last of a specific type override the
previous."

### Reply via `{reply, From, Reply}`

Used to reply to a `{call, From}` event. Either via the transition action
`{reply, From, Reply}` in an action list, or by calling
`gen_statem:reply(From, Reply)` from the callback module. Convenient in
`{keep_state, ...}` returns when you want to stay in the current state
regardless of which it is (crawl 04). Note: `reply/2,3` replies are not visible
in sys debug output (crawl 12, Verbatim quotes: "A reply sent with this
function is not visible in sys debug output.").

### Postpone

`{postpone, true}` (or atom `postpone`) postpones the current event; retried
after a state change (`OldState =/= NewState`). Models selective receive
explicitly for a single received event. Ignored from `init/1` and `enter_loop`
(no event to postpone). Not allowed from state enter calls (crawl 12,
"Timeouts (event / state_timeout / generic) and postpone").

From crawl 04 (Verbatim quote 14, "Postponing Events"): "A postponed event is
retried after a state change, that is, OldState =/= NewState."

### State callback return values

- `{next_state, NextState, NewData [, Actions]}` — set next state and update server data; if `Actions` present, execute transition actions. If `NextState =/= State` it is a state change: the event queue is restarted from the oldest postponed event, any current state time-out is canceled, and a state enter call is performed (if enabled). The current `State` becomes `OldState` in a state enter call.
- `{keep_state, NewData [, Actions]}` — same as `next_state` with `NextState =:= State` (no state change).
- `keep_state_and_data` | `{keep_state_and_data, Actions}` — same as `keep_state` with `NewData =:= Data`.
- `{repeat_state, NewData [, Actions]}` | `repeat_state_and_data` | `{repeat_state_and_data, Actions}` — same as `keep_state`/`keep_state_and_data`, but if state enter calls are enabled, repeat the state enter call as if the state was entered again. In this case `State` and `OldState` become equal in the repeated state enter call.
- `{stop, Reason [, NewData]}` — stop the server with reason `Reason`; if `NewData` present, first update server data.
- `{stop_and_reply, Reason, [NewData,] ReplyActions}` — same as stop values, but first execute the given transition actions that may only be reply actions.
- `stop` — == `{stop, normal}`.

### `code_change/4`

`code_change(OldVsn | {down, term()}, OldState, OldData, Extra) -> {ok, NewState, NewData} | Reason`. The callback mode may be changed due to a code upgrade/downgrade or when changing the callback module. If `callback_mode` should change, it MUST be done via `code_change/4` (else new callback mode not honoured → crash). Returning a failure `Reason` cannot be an `{ok,_,_}` tuple (regarded as success) nor `{ok,_}` (also invalid); recommended: an atom (wrapped in `{error, Reason}`). A release upgrade/downgrade with `Change = {advanced, Extra}` when `code_change/4` is not implemented crashes with `undef` (crawl 12, "Strict rules").

### Differences from `gen_fsm`

`gen_statem` replaces `gen_fsm` since Erlang/OTP 20.0. Features beyond `gen_fsm`
(crawl 12, Purpose): co-located state code, arbitrary term state, event
postponing, self-generated events, state time-out, multiple generic named
time-outs, absolute time-out time, automatic state enter calls, reply from
other state, multiple replies, changing the callback module.

### Catch-all receive

From crawl 04 (Verbatim quote 15, "Selective Receive"): "A catch-all receive
should never be used from a gen_statem behaviour (or from any gen_*
behaviour), as the receive statement is within the gen_* engine itself."

A catch-all receive can discard system messages leading to unexpected
behaviour. If a selective receive must be used, ensure only pertinent messages
are received, and the callback must return in due time so the engine can
handle system messages (crawl 04, "Strict rules / invariants").

### State enter call restrictions

From crawl 04 (Verbatim quote 10, "State Enter Calls"): "Since the state enter
call is not an event there are restrictions on the allowed return value and
state transition actions. You must not change the state, postpone this
non-event, insert any events, or change the callback module."

From crawl 12 (Verbatim quotes): "Should you return `{next_state, NextState,
...}` with `NextState =/= State` the gen_statem crashes." (from a state enter
call); "It is not allowed to change states from this call." (state enter call).

Use `{keep_state, ...}` / `keep_state_and_data` from enter calls (crawl 12,
"Strict rules").

### Start functions

- `start_link/3,4` — linked; must be used if the gen_statem is part of a supervision tree.
- `start/3,4` — standalone (not linked); cannot be used by a supervisor to start a child.
- `start_monitor/3,4` — since OTP 23.0; monitored, not linked; likewise cannot be used by a supervisor to start a child.
- `enter_loop/4,5,6` — requires the calling process to have been started by a proc_lib start function; if `Server` is a `server_name()` it must already be registered.
- `spawn_opt` `monitor` is not allowed in start options (badarg) (crawl 12, Verbatim quotes: "Using spawn option `monitor` is not allowed, it causes a `badarg` failure.").

### `callback_mode/0` body

From crawl 12 (Verbatim quotes): "If this function's body does not return an
inline constant value the callback module is doing something strange." (re:
`callback_mode/0`).

## Practical rules

1. Choose `state_functions` when states are atoms and you want code
   co-located by state. Choose `handle_event_function` when the state is a
   compound term or when you prefer a single central dispatcher.
2. Always implement `callback_mode/0`. Returning a list with `state_enter` is
   optional; `callback_mode/0` body should return an inline constant value.
3. In `state_functions` mode the state MUST be an atom; `StateName` cannot be
   `terminate` (collides with `Module:terminate/3`).
4. Use action lists for side effects: replies, timeouts, `next_event`,
   `postpone`, `hibernate`. Do not perform side effects by directly calling
   state callback functions from other callbacks.
5. Use `postpone` only when an event cannot be handled in the current state
   but should be retried after a state change. Postponed events are retried
   only on state changes (`OldState =/= NewState`), not on `keep_state`.
6. Use the `internal` event type for self-generated events via
   `{next_event, internal, Content}`. This keeps them distinguishable from
   external events.
7. Prefer `{reply, From, Reply}` actions over `gen_statem:reply/1,2` unless
   the reply must be sent from a different callback or from code outside the
   normal return path.
8. Use state timeouts for "this state must not last longer than N ms". Use
   generic timeouts for independent named timers. Use event timeouts for "do X
   if nothing happens for N ms".
9. From a state enter call: do not change state, do not postpone, do not insert
   events, do not change callback module. Use `{keep_state, ...}` /
   `keep_state_and_data`.
10. Keep `init/1` fast. A `postpone` action from `init/1` is ignored (no event
    to postpone).
11. Never use a catch-all `receive` from a `gen_statem` (or any `gen_*`)
    behaviour.
12. If `callback_mode` should change, it MUST be done via `code_change/4`.

## Review checklist

- [ ] The problem is genuinely a state machine before choosing `gen_statem`.
- [ ] `callback_mode/0` returns exactly one of the documented forms; body returns an inline constant value.
- [ ] In `state_functions` mode, no state is named `terminate`.
- [ ] State callbacks return valid `gen_statem` result tuples.
- [ ] `{reply, From, Reply}` is used in action lists, not raw `reply/1,2`,
      unless the reply path requires it.
- [ ] `postpone` is paired with a clear state change that will retry the event.
- [ ] The three timeout kinds are used appropriately and their cancellation
      semantics are documented.
- [ ] `state_enter` callbacks do not change the state, postpone, insert events,
      or change callback module; they return `{keep_state, ...}` /
      `keep_state_and_data`.
- [ ] `init/1` does not perform blocking work that should be deferred.
- [ ] `code_change/4` returns `{ok, NewState, NewData}` on success; failure
      `Reason` is not an `{ok,_,_}` or `{ok,_}` tuple.
- [ ] `format_status/1` (not deprecated `format_status/2`) redacts sensitive
      data from `sys` output and crash logs.
- [ ] No catch-all `receive` in the callback module.
- [ ] `spawn_opt` does not include `monitor`.
- [ ] `:sys` debug options are removed or disabled in production.

## Implementation checklist

- [ ] Decide `state_functions` vs `handle_event_function` up front.
- [ ] Decide whether `state_enter` is needed for per-state entry logic.
- [ ] Implement `init/1`, `callback_mode/0`, and the required state callback(s).
- [ ] Implement `terminate/3` only if cleanup is best-effort and safe (return
      value is ignored).
- [ ] Implement `code_change/4` if release upgrades are planned; change
      `callback_mode` here if needed.
- [ ] Implement `format_status/1` (since OTP 25.0) if the state contains
      secrets; do not use deprecated `format_status/2`.
- [ ] Add client API wrappers for `start_link/4`, `call/2,3`, `cast/2`, and
      `stop/1,3`.
- [ ] Use `start_link/3,4` for supervised processes; `start/3,4` standalone;
      `start_monitor/3,4` (since OTP 23.0) for monitored, non-linked.
- [ ] Add `-spec` declarations for public functions and callbacks.
- [ ] Add unit or common-test coverage for each state transition and each
      timeout path.
- [ ] Disable `:sys` tracing before shipping.

## Runtime / debugging checklist

- [ ] Confirm the process is registered or supervised as expected.
- [ ] Use `:sys.get_state/1` to inspect `{State, Data}` at runtime.
- [ ] Use `:sys.get_status/1` to inspect formatted status (note: `reply/2,3`
      replies are not visible in sys debug output).
- [ ] Use `:sys.trace(pid, true)` to observe event dispatch and transitions.
- [ ] Verify that replies to `call/3` are not timing out because of a missing
      `{reply, From, Reply}` action.
- [ ] Verify that `postpone`d events are not stuck because no state change
      occurs.
- [ ] Verify that state timeouts are cancelled by intended state changes.
- [ ] Confirm that `terminate/3` runs during normal shutdown by sending
      `gen_statem:stop/1` to a process that traps exits.
- [ ] For reasons other than `normal`, `shutdown`, `{shutdown, Term}` an error
      report is issued via `logger`.

## Validation hooks

- `erlc -W0` / `rebar3 compile` / `mix compile` — catch missing callbacks,
  bad return shapes, and arity errors.
- `dialyzer` — verify `-spec` contracts and callback return types.
- `eunit` or `common_test` — exercise every state transition, timeout, and
  error path.
- Manual review of action lists — compilers do not validate that a `reply`
  action is emitted for every `call` event.
- Note explicitly: markdown documentation cannot be compiled; validate code
  blocks by reading them against the official callback contracts in crawl 12.

## Examples

### Callback signatures (verbatim from crawl 12)

```erlang
%% Mandatory
-callback init(Args :: term()) -> init_result(state()).
%% init_result(StateType, DataType) ::
%%     {ok, State, Data}
%%   | {ok, State, Data, Actions :: [action()] | action()}
%%   | ignore
%%   | {stop, Reason :: term()}
%%   | {error, Reason :: term()}.   % {error,_} since OTP 26.0

-callback callback_mode() -> callback_mode_result().
%% callback_mode_result() :: callback_mode() | [callback_mode() | state_enter()].
%% callback_mode() :: state_functions | handle_event_function.
%% state_enter()  :: state_enter.

%% State callback in state_functions mode (optional, one per state atom)
-callback 'StateName'(enter, OldStateName :: state_name(), data()) ->
                state_enter_result(state_name());
            (EventType :: event_type(), EventContent :: event_content(), Data :: data()) ->
                event_handler_result(state_name()).
%% StateName cannot be `terminate` (collides with terminate/3).

%% State callback in handle_event_function mode (optional)
-callback handle_event(enter, OldState, CurrentState, Data) ->
                state_enter_result(CurrentState)
            when OldState :: state(), CurrentState :: state(), Data :: data();
          (EventType, EventContent, CurrentState, Data) ->
                event_handler_result(state())
            when EventType :: event_type(),
                 EventContent :: event_content(),
                 CurrentState :: state(),
                 Data :: data().

%% Optional
-callback code_change(OldVsn :: term() | {down, term()},
                      OldState :: state(), OldData :: data(), Extra :: term()) ->
        {ok, NewState :: state(), NewData :: data()} | (Reason :: term()).

-callback format_status(Status) -> NewStatus
        when Status :: format_status(), NewStatus :: format_status().   % since OTP 25.0

-callback format_status(StatusOption, [[{Key,Value}] | state() | data()]) -> Status :: term()
        when StatusOption :: normal | terminate.   % DEPRECATED; use format_status/1

-callback terminate(Reason :: normal | shutdown | {shutdown, term()} | term(),
                    CurrentState :: state(), data()) -> any().
```

### Supporting types (verbatim from crawl 12)

```erlang
-type state()       :: state_name() | term().
-type state_name()  :: atom().
-type data()        :: term().
-type from()        :: {To :: pid(), Tag :: reply_tag()}.
-type event_type()  :: external_event_type() | timeout_event_type() | internal.
-type external_event_type() :: {call, From :: from()} | cast | info.
-type timeout_event_type()  :: timeout | {timeout, Name :: term()} | state_timeout.
-type event_content() :: term().
```

### Return-shape blocks (verbatim from crawl 12)

#### `init_result(StateType, DataType)`

```erlang
{ok, State, Data}
| {ok, State, Data, Actions :: [action()] | action()}
| ignore
| {stop, Reason :: term()}
| {error, Reason :: term()}   % since OTP 26.0
```

#### `event_handler_result(StateType, DataType)` (state callback after an event)

```erlang
{next_state, NextState, NewData}
| {next_state, NextState, NewData, Actions :: [action()] | action()}
| state_callback_result(action(), DataType)
```

`{next_state, NextState, NewData [, Actions]}` — state transition to `NextState`
(may equal current state); sets `NewData`; executes `Actions`. If
`NextState =/= CurrentState` it is a state change.

#### `state_callback_result(ActionType, DataType)` (common to event & enter calls)

```erlang
{keep_state, NewData}
| {keep_state, NewData, Actions :: [ActionType] | ActionType}
| keep_state_and_data
| {keep_state_and_data, Actions :: [ActionType] | ActionType}
| {repeat_state, NewData}
| {repeat_state, NewData, Actions :: [ActionType] | ActionType}
| repeat_state_and_data
| {repeat_state_and_data, Actions :: [ActionType] | ActionType}
| stop
| {stop, Reason :: term()}
| {stop, Reason :: term(), NewData :: DataType}
| {stop_and_reply, Reason :: term(), Replies :: [reply_action()] | reply_action()}
| {stop_and_reply, Reason :: term(), Replies :: [reply_action()] | reply_action(), NewData :: DataType}
```

Note (crawl 12, Verbatim quotes): "All these terms are tuples or atoms and
will be so in all future versions of gen_statem."

#### `state_enter_result(State, DataType)` (state callback after a state enter call)

```erlang
{next_state, State, NewData}                       % State MUST equal current state
| {next_state, State, NewData, Actions :: [enter_action()] | enter_action()}
| state_callback_result(enter_action(), DataType)
```

From a state enter call: `postpone` is not allowed; `{next_event,_,_}` is not
allowed; changing state is not allowed (crash if `NextState =/= State`).

### Action types (verbatim from crawl 12)

#### `action()` (transition actions; not allowed from state enter calls)

```erlang
postpone
| {postpone, Postpone :: postpone()}
| {next_event, EventType :: event_type(), EventContent :: event_content()}
| {change_callback_module, NewModule :: module()}   % since OTP 22.3
| {push_callback_module, NewModule :: module()}     % since OTP 22.3
| pop_callback_module                               % since OTP 22.3
| enter_action()
```

where

```erlang
-type enter_action() ::
        hibernate
      | {hibernate, Hibernate :: hibernate()}
      | timeout_action()
      | reply_action().
-type reply_action() :: {reply, From :: from(), Reply :: term()}.
-type postpone() :: boolean().
-type hibernate() :: boolean().
```

#### `enter_action()`, `reply_action()`, `postpone()`, `hibernate()`

See block above.

#### `timeout_action()`, `timeout_cancel_action()`, `timeout_update_action()`, `timeout_option()`

```erlang
-type timeout_action() ::
        (Time :: event_timeout())                                              % short for {timeout, Time, Time}
      | {timeout, Time :: event_timeout(), EventContent}
      | {timeout, Time, EventContent, Options :: timeout_option() | [timeout_option()]}
      | {{timeout, Name :: term()}, Time :: generic_timeout(), EventContent}
      | {{timeout, Name}, Time, EventContent, Options}
      | {state_timeout, Time :: state_timeout(), EventContent}
      | {state_timeout, Time, EventContent, Options}
      | timeout_cancel_action()       % since OTP 22.1
      | timeout_update_action();      % since OTP 22.1
-type timeout_cancel_action() ::
        {timeout, cancel} | {{timeout, Name :: term()}, cancel} | {state_timeout, cancel};
-type timeout_update_action() ::
        {timeout, update, EventContent}
      | {{timeout, Name :: term()}, update, EventContent}
      | {state_timeout, update, EventContent};
-type timeout_option() :: {abs, Abs :: boolean()}.
```

### Door state machine (`state_functions`)

A door with `locked` and `open` states. `card` unlocks, `close` closes an
open door, and a state timeout auto-locks an open door after 10 seconds.

```erlang
-module(door).
-behaviour(gen_statem).

-export([start_link/0, card/1, close/0, stop/0]).
-export([init/1, callback_mode/0, terminate/3, code_change/4]).
-export([locked/3, open/3]).

-define(AUTO_LOCK_MS, 10000).

start_link() ->
    gen_statem:start_link({local, ?MODULE}, ?MODULE, [], []).

card(Code) ->
    gen_statem:call(?MODULE, {card, Code}).

close() ->
    gen_statem:call(?MODULE, close).

stop() ->
    gen_statem:stop(?MODULE).

init([]) ->
    {ok, locked, #{code => 1234}}.

callback_mode() ->
    state_functions.

terminate(_Reason, _State, _Data) ->
    ok.

code_change(_OldVsn, State, Data, _Extra) ->
    {ok, State, Data}.

%% -- locked state

locked({call, From}, {card, Code}, #{code := Code} = Data) ->
    {next_state, open, Data, [{reply, From, unlocked}]};
locked({call, From}, {card, _WrongCode}, Data) ->
    {keep_state, Data, [{reply, From, invalid_card}]};
locked({call, From}, close, Data) ->
    {keep_state, Data, [{reply, From, already_locked}]}.

%% -- open state

open({call, From}, close, Data) ->
    {next_state, locked, Data, [{reply, From, locked}]};
open(state_timeout, auto_lock, Data) ->
    {next_state, locked, Data};
open(enter, _OldState, Data) ->
    %% Start auto-lock timer every time we enter open.
    {keep_state, Data, [{state_timeout, ?AUTO_LOCK_MS, auto_lock}]}.
```

Note: `callback_mode/0` here returns `state_functions` (not
`[state_functions, state_enter]`), yet the `open/3` clause handles `enter`.
To actually receive state enter calls, `callback_mode/0` must return
`[state_functions, state_enter]`.

## Common mistakes

1. **Forgetting `callback_mode/0`** — the behaviour will not start without it;
   the body should return an inline constant value.
2. **Using `terminate` as a state name in `state_functions` mode** — it
   collides with the optional `Module:terminate/3` callback.
3. **Returning a `reply` tuple like `gen_server`** — `gen_statem` uses
   `{reply, From, Reply}` actions, not `{reply, Reply, NewState}`.
4. **Calling state callback functions directly** — always let the engine
   dispatch events. Use `{next_event, internal, ...}` to trigger another state
   callback.
5. **Expecting `postpone` to retry on `keep_state`** — postponed events are
   retried only on state changes (`OldState =/= NewState`).
6. **Confusing the three timeout kinds** — event timeouts are cancelled by any
   event (including postponed/inserted); state timeouts are cancelled by state
   changes; generic timeouts are independent named timers with no auto-cancel.
7. **Changing state inside a state enter call** — enter calls must return the
   current state; returning `{next_state, NextState, ...}` with
   `NextState =/= State` crashes the gen_statem. Use `repeat_state` to re-enter.
8. **Inserting events or postponing from a state enter call** — not allowed.
9. **Blocking in `init/1`** — keep `init/1` fast; a `postpone` action from
   `init/1` is ignored.
10. **Relying on `terminate/3` for critical cleanup** — return value is
    ignored; not guaranteed on brutal kill or when exits are not trapped.
11. **Using a catch-all `receive`** — never use from a `gen_statem` (or any
    `gen_*`) behaviour; the receive is within the `gen_*` engine and can
    discard system messages.
12. **Using `spawn_opt` `monitor`** — not allowed in start options; causes a
    `badarg` failure.
13. **Expecting `reply/2,3` replies in sys debug output** — they are not
    visible there.
14. **Expecting zero-timeout to behave like `receive ... after 0`** —
    `{timeout, 0}` does not receive any external event, unlike Erlang's
    `receive ... after 0 ... end` (and unlike `gen_server`).

## Strict vs contextual guidance

### Strict

- A `gen_statem` callback module MUST implement `init/1` and
  `callback_mode/0`.
- `callback_mode/0` MUST return exactly one of the documented forms; the body
  should return an inline constant value.
- State callbacks MUST return valid `gen_statem` result tuples; bad returns
  terminate the process.
- In `state_functions` mode, the state name `terminate` MUST NOT be used.
- Replies to `call/3` MUST be produced by `{reply, From, Reply}` actions or by
  `gen_statem:reply/1,2`; do not invent return tuples.
- State enter calls MUST NOT change the state, postpone, insert events, or
  change the callback module.
- `code_change/4` returning a failure `Reason` MUST NOT be an `{ok,_,_}` or
  `{ok,_}` tuple.
- If `callback_mode` should change, it MUST be done via `code_change/4`.
- `spawn_opt` `monitor` MUST NOT be used in start options.
- `format_status/2` is deprecated; use `format_status/1` (since OTP 25.0).
- A catch-all `receive` MUST NEVER be used from a `gen_statem` (or any
  `gen_*`) behaviour.
- `start_link/3,4` MUST be used if the gen_statem is part of a supervision
  tree; `start/3,4` and `start_monitor/3,4` cannot be used by a supervisor to
  start a child.
- `enter_loop` requires the calling process to have been started by a proc_lib
  start function.

### Contextual tradeoffs

- Choose `state_functions` for readability when states are atoms and
  independent.
- Choose `handle_event_function` when the state is a compound term or when
  centralized dispatch is clearer (enables non-atom, complex, or hierarchical
  states).
- Use `postpone` for selective-receive-style event deferral.
- Use `state_enter` for per-state entry logic that must run on every
  transition into a state.
- Use `hibernate` only for large-heap, long-idle processes.
- Prefer `{reply, From, Reply}` actions over `gen_statem:reply/1,2` unless the
  reply must be sent from a different callback or from outside the normal
  return path.

## Policy decisions for individual repos

- Whether to require `-spec` on all public client functions and callbacks.
- Whether `state_enter` is the default for all new `gen_statem` modules.
- Preferred callback mode (`state_functions` vs `handle_event_function`).
- Whether dynamic names must use `{via, Module, Name}` or local atoms.
- Lint stack: enable `erlc +warnings_as_errors`, `dialyzer`, `Elvis`, etc.
- Whether `:sys` debug options are permitted in production code at all.
- Restart/shutdown policy for `gen_statem` workers under supervisors.
- Whether `gen_statem:send_request`/`wait_response` patterns are preferred
  over plain `call/3` for long-running work.
